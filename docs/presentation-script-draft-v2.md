### [1:45 ~ 2:45] 슬라이드 6: 핵심 실증 사례 — INSP-001669

*(결과 화면 슬라이드를 가리키며)*  
"이 시스템의 판정 원리를 보여주는 가장 대표적인 실제 증거가 디스크에 영구 보존된 **`INSP-001669` 검사 사례**입니다.

화면의 검사 기록을 보시면, PatchCore 모델이 계산한 이상 점수는 `31.5006`이었습니다. 독립 검증 데이터로 산출한 고정 결정 임계값인 `34.1442`보다 낮았기 때문에 모델 단독 소견은 **`OK`(정상)**이었습니다.

하지만 서버의 최종 판정은 OK가 아니라 **`REINSPECT`(재검사)**로 확정되었습니다.  
함께 측정된 Crop의 평균 밝기가 `57.41`로, 정상 기준 하한인 `125.0`에 크게 미달했기 때문입니다.  
물론 이 어두운 밝기가 실제 조명 조도 저하인지, 카메라 노출 문제인지, 아니면 어두운 컨베이어 배경 영역이 포함되었기 때문인지는 물리적으로 확정할 수 없습니다. 하지만 저희 시스템은 원인이 확인되지 않은 저조도 상태에서 섣불리 합격시키지 않고, 6대 우선순위 규칙에 따라 '재검사'로 안전하게 분류했습니다.  
이 검사는 291×278 크기의 실제 Crop PNG, 2차원 결함 히트맵 아티팩트, 그리고 6건의 타임라인 로그와 결합되어 보존되어 있습니다."

### [3:00 ~ 4:30] 3. 무감독 이상 탐지 원리와 PatchCore 벤치마크

"비전 결함 검출 엔진인 **PatchCore**의 원리를 설명하겠습니다.

쉬운 비유를 들자면, PatchCore는 **'정상 병 사진 수천 장이 꽂힌 도감'**을 머릿속에 외우고 있는 검사관입니다.  
공장에서 불량 병 사진을 수집하는 것은 매우 어렵습니다. PatchCore는 정상 병 180장의 패치 임베딩을 ResNet-18 백본으로 추출한 뒤, Coreset 서브샘플링을 통해 메모리 뱅크(`[9216, 384]`, 24MB)에 압축 보관합니다.  
새로운 병이 들어오면, 이미지의 각 패치를 도감 속 정상 패치들과 비교하여 **가장 닮지 않은 최대 거리**를 구합니다. 이 거리가 바로 **이상 점수(Anomaly Score)**입니다.

저희는 독립된 정상 검증셋 29장의 통계를 기반으로 고정 결정 임계값 **`34.1442` ($\mu + 3\sigma$)**를 산출했습니다. 점수가 이 임계값을 넘으면 모델 소견은 NG, 이하면 OK가 됩니다. 과거 단독 CPU 추론 벤치마크 측정치는 평균 **42.53ms**를 기록했습니다.

하지만 모델의 한계도 명확합니다. 과거 83장 테스트 세트 평가에서 Precision은 100%였으나 Recall은 **50.79%**에 머물렀습니다. 대형 파손 32건은 완벽히 검출했지만, 31건의 미세 크랙이나 옅은 오염 결함에서는 임베딩 거리가 정상군과 뚜렷이 분별되지 못했습니다. 저희는 이 한계를 숨기지 않고 뒤에서 말씀드릴 OpenCV 기하 검사와 Gemini 멀티모달 보조 분석으로 풀어나가고 있습니다."

### [4:30 ~ 6:00] 4. 영상 품질 검사와 6대 우선순위 판정: INSP-001669 실증

"VisionInsight의 핵심 안전장치는 **'모델 소견'과 '서버 최종 판정'의 엄격한 분리**입니다.

이를 이해하기 위해 쉬운 비유를 들겠습니다.  
시험을 치르는 수험생이 문제를 몰라서 틀린 것은 '실력 부족(제품 불량 NG)'입니다.  
하지만 시험 도중 정전이 되어 시험지가 안 보여서 답을 못 썼다면, 그 학생을 탈락시켜야 할까요? 아닙니다. 불을 켜고 '재시험(REINSPECT)'을 보게 해야 합니다.

저희 서버의 `decision.py`는 6대 우선순위 규칙을 가집니다.
1. 파이프라인 실패 $\rightarrow$ `ERROR`
2. **영상 품질 경고(조도 저하 등) $\rightarrow$ `REINSPECT` (모델 소견보다 무조건 우선!)**
3. 모델 미완료 또는 소견 불능 $\rightarrow$ `REINSPECT`
4. 품질 정상 + 모델 NG $\rightarrow$ `NG`
5. 품질 정상 + 모델 OK $\rightarrow$ `OK`
6. 기타 미정의 상태 $\rightarrow$ `REINSPECT`

이 규칙이 실제로 입증된 증거가 오늘 디스크에 기록된 **`INSP-001669` 검사**입니다.
- **ROI Crop:** 291×278 해상도, SHA256 `ad028428...`
- **이상 점수:** `31.5006` (임계값 34.1442 이하 $\rightarrow$ **모델 소견: OK**)
- **평균 밝기:** `57.41` (정상 기준치 125.0 미달 $\rightarrow$ **품질: WARNING_LOW_BRIGHTNESS**)
- **서버 최종 판정:** **`REINSPECT`**

영상의 밝기가 57.41로 낮다는 관측값은 확인되었으나, 구체적인 원인이 조명 장치 고장인지, 카메라 노출인지, 어두운 컨베이어 배경 때문인지는 소프트웨어만으로 확정할 수 없습니다. 그럼에도 저희 판정 엔진은 모델의 정상 판정을 그대로 믿지 않고, 안전을 위해 최종 판정을 REINSPECT로 확정했습니다. 이 검사는 단조 증가 ID로 묶여 6건의 타임라인 로그, Anomaly Map 3종 아티팩트와 100% 정합성을 유지하고 있습니다."

"산업 현장에서 자동화 시스템이 갖추어야 할 마지막 덕목은 **'공정 마비 방지'**입니다.

# [산출물 4] 현실적인 비상 시연 대안 (Fallback Scenarios)

서버 재시작, 세션 만료, 외부 API 차단 등 실제 현장에서 발생할 수 있는 장애 상황에 대비한 **100% 동작 보장형 비상 시연 매뉴얼**입니다.

│                        장애 발생 시 3대 비상 경로                       │

  *"현재 라이브 비디오 세션의 보안 쿠키가 만료되었습니다. 세션 간섭을 배제하고 시스템의 결정론적 판정 원리를 보여드리기 위해, 검증된 정적 검사 프리셋인 `[T03:Warn]`을 즉시 로드하겠습니다. 보시는 바와 같이 조도 저하 시 모델 판정과 무관하게 최종 REINSPECT가 도출되는 동일한 안전 규칙을 확인하실 수 있습니다."*

### Q1. 프론트엔드와 백엔드를 별도 포트로 분리한 이유와 발생한 문제는?

  이 과정에서 `localhost:5173`과 `127.0.0.1:8000` 간 크로미움의 `SameSite=Strict` 세션 쿠키 전송 차단으로 인한 Grab 401 오류가 발생했습니다. 저희는 백엔드의 엄격한 보안을 허물지 않고, Vite 프록시(`/api`)를 도입해 브라우저 관점의 단일 출처(Same-Origin) 구조를 완성하여 정석으로 해결했습니다."

### Q2. PostgreSQL과 JSONL을 함께 쓰는 기술적 이유는?
- **답변:**  
  "데이터의 **수정 가능성(Mutability)**에 따른 최적화입니다.  
  작업자가 마우스로 지정하는 ROI 설정은 품종에 따라 수시로 수정되고 관리자 버전 승인을 거쳐야 하므로 관계형 모델이 적합하여 **PostgreSQL**을 사용했습니다.  
  반면, 검사 결과와 생명주기 이벤트 로그는 사후 감사 시 위변조되어서는 안 되는 공정 블랙박스입니다. 비록 물리적 WORM 드라이브는 아니지만, 애플리케이션 레벨에서 수정이 불가능한 **Append-only JSONL**을 적용하고 SHA256 기준 해시와 비교 검증하여 무결성을 확보했습니다."

### Q3. 비지도 이상 탐지 모델 중 PatchCore를 선택한 이유는?
- **답변:**  
  "공정 환경에서는 불량 데이터의 수집과 라벨링이 극히 어렵기 때문에 정상 이미지만으로 학습하는 무감독(Unsupervised) 모델이 필수적입니다.  
  PatchCore는 사전 학습된 ResNet 임베딩의 Coreset 메모리 뱅크를 활용하여 **CPU 단일 코어에서도 평균 42ms대의 저지연 추론**이 가능하며, 이상 점수뿐만 아니라 **2차원 결함 위치(Anomaly Map)를 단 1회 추론에서 정확히 추출**할 수 있어 채택했습니다."

### Q14. 클라우드(Google Cloud Run) 배포 시 고려해야 할 엔지니어링 과제는?
- **답변:**  
  "Cloud Run은 무상태(Stateless) 컨테이너이므로 로컬 디스크 저장이 영구적이지 않습니다.  
  따라서 로컬 JSONL 및 Sidecar 아티팩트를 **Google Cloud Storage(GCS)** 버킷으로 영구 동기화해야 하며, 브라우저 세션 유지를 위해 Nginx 리버스 프록시 또는 Cloud Run의 경로 기반 URL 매핑을 동일 출처(Same-Origin)로 구성해야 합니다."

### Q15. 현재 시점에서 프로젝트의 정직한 개발 완료 수준은?
- **답변:**  
  "정직하게 말씀드리면 다음과 같습니다.  
  - **완전 구현 및 오프라인 검증 완료:** H.264 영상 Grab, 무손실 Crop, 실제 PatchCore 추론 및 아티팩트 영구 보존(`INSP-001669`), 결정론적 6대 판정 분기, 동일 개체 확인 기반 3회 재검사 상한, 4000% Canvas 뷰어.  
  - **오프라인 검증 완료 (LIVE 대기):** Gemini Diagnostic Agent 도구 연동(과거 실서버 통과, 신규 리팩터링 완료), Gemini Vision Judge 지침 및 격리 스키마(오프라인 216 PASS 통과).  
  - **진행 중 및 향후 과제:** Gemini Vision Judge의 실시간 LIVE API 통신 연동, 컨베이어 센서 트리거 기반의 완전 자동(AUTO) PLC 검사 파이프라인.  
  저희는 미완성 기능을 완성되었다고 포장하지 않으며, 견고하게 검증된 백엔드와 데이터 무결성을 바탕으로 다음 단계로 나아가고 있습니다."
