## 0. 이 문서를 관리하는 방법

이 파일은 한 번 쓰고 끝내는 보고서가 아니라, **새 기능·버그 수정·성능 분석·검증·운영 개선이 완료될 때마다 누적하는 변경 이력**이다.

1. **2026-10-20 발표 기준선은 고정한다.** 이미 발표 당시 존재하던 기능을 10월 21일 이후 신규 구현으로 기록하지 않는다.
2. 새 변경을 수행한 후 **아래 `변경 이력` 표와 날짜별 상세 기록에 새 항목을 추가한다.** 기존 항목을 지우거나 다른 날짜로 옮기지 않는다.
3. 각 항목에 **변경 전/후, 실제 변경 파일, 검증 방법·결과, 상태, 남은 한계**를 명시한다.
4. 상태는 `구현·검증 완료`, `구현·추가 검증 필요`, `분석 완료`, `설계·미구현`, `PARTIAL`, `BLOCKED`, `미확인`을 구분해 사용한다.
5. **Codex 실행용 프롬프트 작성은 기능 구현 완료를 뜻하지 않는다.** 도구·모델·서버를 실제로 실행했다는 증거가 없다면 검증 완료로 표시하지 않는다.
6. 모델 검출력 향상, 캐시 실제 확보량, 신규 API 실호출 성공 등은 **측정·실행 증거가 있을 때만** 결과로 기록한다.
7. 기존 `IMG-GRAB-<UUID>.png/.json`, `image_id`/`inspection_id` 매핑, 검사 이력 및 원본 증거는 이 문서를 갱신한다는 이유로 변경하지 않는다.
8. 코드와 동기화할 때 **동일한 변경 작업의 일부로** 이 문서를 갱신한다. 이 문서만으로 자동 백그라운드 갱신이 이루어지지는 않는다.

### 새 변경 기록 템플릿

새 작업이 발생하면 `6. 날짜별 변경 이력`의 맨 위에 다음 양식을 복사해 작성한다.

```markdown
### YYYY-MM-DD — VI-CHG-YYYYMMDD-NNN — 변경 제목

- **영역:** 검사 / 품질 / UI / Gemini / 데이터 / 테스트 / 운영 / 문서 중 선택
- **변경 전:** 기존 문제 또는 동작
- **변경 후:** 실제로 달라진 동작·파일·계약
- **변경 파일:** 실제 저장소 상대경로
- **검증:** 실행 명령 또는 검증 방법, PASS/FAIL/SKIP 및 증거 경로
- **상태:** 구현·검증 완료 / 구현·추가 검증 필요 / 분석 완료 / 설계·미구현 / PARTIAL / BLOCKED / 미확인
- **영향·호환성:** 기존 이미지, Image Manifest, RIG, DB, API 등에 대한 영향
- **제약 및 다음 작업:** 확인하지 못한 사항과 후속 단계
```

## 3. 영역별 상세 개선·검증 근거

### 3.1 검사 데이터의 추적성과 무결성 강화

**발표 당시**에도 영상·프레임·ROI, `Capture ID`, `Image ID`, `Inspection ID`, SHA256 및 실행 로그가 연결되어 있었다. 발표 이후 변경은 기존 추적 기능의 **명칭 명확화와 추가 검증**이다.

- 이미지와 같은 stem을 가진 JSON 메타데이터를 **Image Manifest**로 부르기로 정리했다. PWA Manifest와 구분하기 위한 용어 변경이다.
- 기존 파일명 `IMG-GRAB-<UUID>.png/.json`, JSON 스키마, ID 매핑 및 경로는 변경하지 않는다.
- `Quality Shadow Metrics Sidecar`는 Image Manifest와 별개의 품질 지표 기록이다.
- 실제 검사 `INSP-001741`의 Crop, 검사 식별자, `crop_sha256`, Sidecar 연결 관계를 확인했다.
- A-4 샘플의 디코딩 후 프레임·Capture·영구 Crop 간 화소 일치도 확인했다.

**증거 기준:** 영구 Crop은 `data/outputs/grab_inspection_inputs/`에 보관되고, Shadow Sidecar는 버전별 `data/outputs/quality_shadow_metrics/`에 별도로 저장된다.

### 3.2 Quality Shadow Metrics 추가 검증 (A-3-2)

Quality Shadow는 서버 판정과 독립적으로 원본 Crop의 화질 지표를 측정·저장하며, 모델의 OK/NG 판정을 대체하지 않는다.

| 항목 | 확인 결과 | 해석 범위 |
|---|---|---|
| 격리 회귀 | 235 PASS / 0 FAIL / 0 SKIP | 해당 테스트 묶음에 한정 |
| 실제 검사 연계 | `INSP-001741` | 실제 검사 1건의 보존·연결 증거 |
| 품질 측정 | 9개 측정 지표 재현 | 지표 산식·연결 검증, 검출 성능 향상 증거 아님 |
| 기존 판정 | 모델 의견·REINSPECT 보존 | Threshold 및 정책 변경 없음 |
| 종합 완료 | **PARTIAL** | Worker 기준선, UI/F5 불변성, 종료/큐 지연 등의 추가 검증 필요 |

실측 예시: Crop **278×276**, 평균 밝기 약 **121.37 GV**. 입력 품질 경고에 따른 서버 `REINSPECT`는 유지되었다.

### 3.3 Grab 화질·선명도 및 전처리 분석 (A-4 Step 1~5)

A-4는 이미지가 실제로 선명해졌다고 발표하는 작업이 아니라, **픽셀의 변화가 일어나는 구간을 분리해 측정한 작업**이다.

| 분석 | 실측·확인 | 한계 |
|---|---|---|
| 디코딩 프레임→Capture→Crop | 해당 샘플에서 다른 픽셀 0, MAE 0 | 인코딩 전 원본과의 동일성 증명은 아님 |
| 외부 모델 전처리 | Crop 278×276 → PIL Bilinear 256×256, RGB·정규화 경로 오프라인 재현 | 서버 런타임 Tensor 확인까지 완료한 것은 아님 |
| Bilinear→Bicubic | 얇은 밝은 림의 peak contrast 약 +4.58% | 특정 국소 ROI의 선명도 지표 |
| Bicubic 부작용 | 범위 밖 Overshoot/Undershoot 280/65,536 픽셀(0.427%) | 링잉·클리핑 영향 추가 분석 필요 |
| 운영 모델 | Bilinear 유지 | Bicubic 적용·성능 향상 주장은 금지 |

실제 결함 라벨에 기반한 전후 평가가 없으므로 **불량 검출 정확도·Recall 향상은 아직 입증되지 않았다**.

### 3.4 재검사 및 작업자 확인 흐름 개편 제안

**기존 정책:** 동일 제품에 대해 PatchCore 검사 1/3·2/3·3/3을 허용하고, 이후 수동 판정 조건을 확인한다.

**새로 합의·분석한 방향(미구현):**

| 순서 | 제안 단계 | 책임 |
|---|---|---|
| 1차 | MANUAL Grab → PatchCore/OpenCV → 서버 판정 | `OK / NG`는 유지, `REINSPECT`면 추가 검토 |
| 2차 | 사용자가 Gemini Vision Judge 명시적으로 실행 | `OK / NG / REINSPECT` 참고 의견; 서버 판정 불변 |
| 3차 | 작업자가 `MANUAL_OK / MANUAL_NG / HOLD` 결정 | 작업자 판단을 별도로 저장, 강제 확정 금지 |

Codex의 읽기 전용 분석에서 다음 사항이 확인됐다.

- RIG에는 단순 횟수 외에 Capture 소유권, 중복 추론 방지, 저장 확정·회복, 검사 이력 및 작업자 판정이 결합되어 있다.
- 기존 세 번째 REINSPECT 뒤 자동 `HOLD` 기록이 생성되는 것이 아니라 `MANUAL_REVIEW_REQUIRED` 상태가 된다. `HOLD`는 작업자가 남기는 별도 결정이다.
- Gemini Judge 저장에도 RIG의 파일 잠금·쓰기 기반 코드가 쓰이므로 RIG 전체 삭제는 위험하다.
- 새 정책은 기존 RIG 자료를 과거 정책으로 조회 가능하게 유지하는 방향이 적합하다.

**현재 상태:** 변경 의존성 분석·정책 제안·Phase 1 구현 프롬프트 작성까지 진행. 실제 Retry 3회 로직 제거와 신규 UI 동작은 **완료 확인되지 않음**.

**현재 상태:** 실제 캐시 삭제량, 확보된 디스크 용량, 자동 정리 코드 반영 및 테스트 성공 여부는 **보고를 받지 못해 미확인**이다.

## 8. 파일 구조 정리 메모 (계획·미적용)

현재 Explorer 화면처럼 `IMG-GRAB-<UUID>.png`와 같은 stem의 `.json`이 나란히 보이는 것은 정상적인 Crop + Image Manifest 쌍이다. **파일명이나 기존 경로를 바꾸지 않고도 화면에서만 묶어 표시**하는 방법을 먼저 검토한다.

- **1순위:** VS Code Explorer의 파일 중첩(File Nesting) 및 필요한 경우 표시 필터 사용. 이미지/JSON의 실제 경로는 그대로 둔다.
- **2순위:** `docs/progress/`, `docs/architecture/`, `docs/reports/` 등 *신규 문서부터* 역할별로 정리. 기존 경로 참조 문서는 무리하게 이동하지 않는다.
- **3순위:** 별도 읽기 전용 경로 영향 조사 후, 승인된 소스·스크립트만 소규모로 단계적 이동 고려.
- **현재 보류:** `data/outputs/grab_inspection_inputs/`, `captures/`, `videos/`, `quality_shadow_metrics/`, 검사 JSONL·RIG 등 실제 검사 데이터를 물리적으로 이동하는 작업.

경로를 변경할 경우 Python/TypeScript의 상수·환경변수·상대경로·동적 경로, API, DB 저장 경로, JSON/JSONL 내부 참조, 테스트 Fixture·PPT·문서 링크, Git ignored 및 Capture TTL까지 조사해야 한다. 일괄 문자열 치환이나 무검증 이동은 금지한다.

> **2026-10-23 제출 전 권장:** 대규모 디렉터리 이동보다는 위의 시각적 정리와 문서 추가까지만 적용하고, 물리적 구조 개편은 별도 작업으로 미룬다.
