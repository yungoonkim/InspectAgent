# VisionInsight — Gemini Computer Use + Playwright E2E 테스트 자동화 실행 계획서

> **문서 상태:** 자동화 실행 및 아키텍처 계획서 (최신 구현 상태 및 피드백 반영 개정판)  
> **프로젝트:** VisionInsight (산업용 Vision 검사 이상 진단 AI Agent)  
> **대상 플랫폼:** Windows 11 (로컬 개발 환경)  
> **실행 주체:** 로컬 Playwright Test Runner (우선 도입) + Gemini Computer Use Bridge (보조 시각 검증, 단계적 도입)  
> **기준 영상:** `VID-000003` 전용 (16초, 480프레임, 30fps, 1920×480, H.264 MP4, 양품/불량 혼합 영상)  
> **제외 영상:** `VID-000001`, `VID-000002` (본 자동화 테스트에서 Grab이나 검사 실행 절대 금지)  
> **개정 일자:** 2026년 10월 20일

## 1. 자동화 아키텍처 및 도구별 역할 분담

### 1.1 하이브리드 검증 아키텍처 및 단계적 도입 순서

VisionInsight E2E 자동화는 **Playwright의 결정론적(Deterministic) 제어 능력**과 **Gemini Computer Use의 시각적·문맥적(Visual & Contextual) 인지 능력**을 결합한 하이브리드 검증 구조를 목표로 합니다.

단, 안정적인 자동화 파이프라인 구축을 위해 **도입 순서를 엄격히 분리**합니다:
1. **1단계 (기본 회귀 자동화):** Playwright 단독의 결정론적 DOM/네트워크/상태 단언 테스트를 먼저 완벽히 구축·안정화합니다.
2. **2단계 (시각 검증 브리지):** Playwright 회귀 테스트가 통과된 이후, 레이아웃 왜곡·텍스트 겹침·오버레이 정합성을 검증하는 Gemini Computer Use 시각 브리지를 추가합니다.

```

### 1.2 상세 역할 분담 매트릭스 및 교차 검증 원칙

| 검증 영역 | Playwright 역할 (1차 결정론적 단언) | Gemini Computer Use 역할 (2차 시각 보조) | 판정 원칙 및 가드레일 |
| :--- | :--- | :--- | :--- |
| **브라우저 제어** | 로컬 Chrome 기동, 포트 연결, 페이지 이동, 뷰포트(1920×1080) 고정 | 브라우저 직접 기동 불가 (전달받은 캡처 분석) | Playwright 단독 제어 |
| **사용자 인터랙션** | 확인된 DOM 셀렉터 클릭, 텍스트 입력, 키보드 조작 | 시각적 힌트 기반 상호작용 가능 여부 확인 | 실제 인터랙션은 Playwright 이벤트만 사용 |
| **DOM 및 상태 단언** | `toBeVisible()`, `toBeDisabled()`, `toHaveValue()` | 렌더링된 텍스트 가독성, 타 레이어에 의한 가림 감지 | **시각 판단만으로 PASS 확정 불가 (DOM 단언 필수)** |
| **네트워크 모니터링** | 프론트엔드 HTTP Status, 스키마 유효성 검증 | 네트워크 상태 뱃지(`STREAM PLAYING`, `FROZEN` 등) 일치 확인 | 브라우저 네트워크 추적 |
| **외부 API 통제** | 브라우저 네트워크 인터셉트 (외부 도메인 차단) | 2차 의견 캡션 및 비활성 안내 문구 시각 확인 | **FastAPI 백엔드 로그 감사 병행 필수** (서버 직접 호출 확인) |
| **시각적 품질 검증** | 픽셀 매칭(Pixelmatch) | **[핵심]** 텍스트 겹침, CSS flex 누락, Edge/Heatmap 정합성 관찰 | DOM 단언 불가 항목은 "육안 확인 필요"로 기록 |

## 2. VID-000003 전용 규칙 및 실제 구현 API 경로

### 2.1 VID-000003 동적 선택 및 안전 가드레일

현재 VisionInsight 환경에는 `VID-000001`~`VID-000003`이 등록되어 있으며, 초기 기본 선택 영상은 `VID-000002`일 수 있습니다.  
따라서 자동화 테스트에서는 단순 중단이 아닌 **동적 선택 및 적용 검증 규칙**을 적용합니다.

1. **테스트 시작 시 영상 선택 UI(`select#live-video-source`)에서 `VID-000003`을 선택합니다.**
2. **실제 적용된 영상 ID가 `VID-000003`인지 확인합니다** (헤더 뱃지 및 드롭다운 value).
3. **선택·검증에 실패한 경우에만 후속 검사 실행을 중단(ABORT)합니다.**
4. **`VID-000001`과 `VID-000002`로는 어떠한 Grab이나 검사도 실행하지 않습니다.**

- **검증된 영상 사양:**
  - 영상 ID: `VID-000003`
  - 재생 길이: 16.0초 (480 프레임, frame_index: 0 ~ 479)
  - 해상도 / 주사율: 1920×480 CFR / 30.00 fps
  - 코덱: H.264 MP4
  - 내용: 양품과 불량 병 원본이 혼합된 컨베이어 시연 영상

---

### 2.2 확인된 실제 API 엔드포인트 목록

테스트 하네스가 대조하고 감시해야 할 백엔드 API 경로는 실제 소스코드(`backend/video_api.py`, `backend/main.py`, `backend/grab_inspection.py`, `backend/vision_review_api.py`)에 기반하여 작성되었습니다.  
*(확인되지 않은 임의의 경로 `/api/video/metadata/...` 등은 사용하지 않습니다.)*

- **비디오 관리 API (`backend/video_api.py`):**
  - `GET /videos`: 등록 비디오 목록 조회
  - `GET /videos/{video_id}`: 단일 비디오 메타데이터 조회
  - `GET /videos/{video_id}/stream`: H.264 비디오 스트리밍
  - `POST /videos/{video_id}/grab`: 프레임 캡처 및 임시 Capture 생성
  - `POST /capture-sessions`: 브라우저 캡처 세션 발급
  - `GET /captures/{capture_id}`: 캡처 메타데이터 조회
  - `GET /captures/{capture_id}/image`: 캡처 이미지 PNG 다운로드
- **검사 및 재검사 API (`backend/main.py`, `backend/grab_inspection.py`):**
  - `POST /captures/{capture_id}/inspect`: Grab 이미지 기반 PatchCore 검사 실행
  - `GET /inspections`: 최근 검사 기록 목록 조회 (`?limit=50`)
  - `GET /inspections/{inspection_id}`: 단일 검사 상세 결과 조회
  - `GET /inspections/{inspection_id}/anomaly-map`: PatchCore 이상지도 메타데이터 조회
  - `GET /inspections/{inspection_id}/anomaly-map/overlay.png`: 이상지도 투명 오버레이 PNG 반환
  - `GET /inspections/{inspection_id}/agent-report`: 저장된 Gemini Agent 진단 보고서 조회
  - `GET /reinspection-groups/{group_id}`: 재검사 그룹 상태 조회
  - `GET /reinspection-groups/by-capture/{capture_id}`: 캡처 연결 재검사 그룹 조회
  - `POST /reinspection-groups/{group_id}/manual-reviews`: 작업자 수동 판정 기록 추가
- **Vision Judge API (`backend/vision_review_api.py`):**
  - `GET /inspections/{inspection_id}/vision-review`: 기존 저장된 Vision Judge 결과 조회
  - `POST /inspections/{inspection_id}/vision-review`: 신규 Vision Judge 분석 요청 (동의 필수)

> [!NOTE]
> 위 목록에 명시되지 않은 컴포넌트 내부 세부 셀렉터, 폼 필드명, 세부 저장 필드는 가상으로 작성하지 않고 **"Codex 구현 시 실제 코드 확인 필요"**로 관리합니다.

## 3. 단계별 자동화 도입 계획 (Phased Rollout)

전체 15개 시나리오는 유지하되, 안전성과 구현 완료 여부에 따라 3단계로 나누어 도입합니다.  
특히 **Phase 1은 시스템 상태 변경이 전혀 없는 5개 핵심 읽기 전용 흐름으로 엄격히 한정**합니다.

```

│ [안전한 읽기 전용]    │ [사전 승인 검사 흐름]   │ [격리된 LIVE API 검증]    │

### 3.1 Phase 1: 핵심 읽기 전용 5대 흐름 (우선 구현 범위)

Phase 1은 백엔드 파일(`inspections.jsonl`, `captures/`)에 쓰기 작업을 일절 발생시키지 않는 5개 읽기 전용 테스트로 구성됩니다. 이미 Codex 구현 및 Chrome 수동 검증이 완료된 TC-11, TC-12가 포함됩니다.

#### 1. TC-01: VID-000003 선택 및 16초 영상 재생
- **위험도:** Level 1 (읽기 전용 UI)
- **주요 검증:** `select#live-video-source`에서 `VID-000003` 동적 선택 및 검증, 16초(480프레임) 비디오의 Play/Pause 및 타임라인 슬라이더 조작.

#### 2. TC-07 + TC-08: 상위·하위 검사 탭 전환 및 상태 보존
- **위험도:** Level 1 (읽기 전용 UI)
- **주요 검증:** 신규 검사를 실행하지 않고 **기존에 저장된 검사 결과**를 로드한 상태에서 상위 탭(`[Grab 검사]` ↔ `[정적 이미지 검사]`) 및 서브탭(`[1차 · PatchCore 검사]` ↔ `[2차 · Gemini Vision Judge]`)을 전환할 때, 컴포넌트 상태(현재 검사 ID, 줌/팬 배율, 입력값)가 유실되지 않고 보존되는지 검증.

#### 3. TC-10: Heatmap, Zoom/Pan, Pixel Inspector
- **위험도:** Level 1 (읽기 전용 UI)
- **주요 검증:** 기존 검사 결과 화면에서 툴바의 `Heatmap` 토글 버튼, 마우스 휠을 통한 줌(Zoom 1.0x~4.0x) 및 드래그 팬(Pan), 마우스 오버 시 `Pixel Inspector` 툴팁(좌표 x, y, 정규화 이상 점수 표시) 연동 검증.

#### 4. TC-11: 병 외곽 및 내부 림 Edge 오버레이
- **구현 상태:** **구현 완료 / Chrome 회귀 자동화 대기** (`BottleEdgeDetails.tsx`)
- **위험도:** Level 1 (읽기 전용 UI)
- **주요 검증:**
  - 병 외곽(초록색 오버레이, `outer.status`) 및 내부 림 후보(노란색 오버레이, `rim.status`) 렌더링.
  - Edge 오버레이 ON/OFF 토글 지원.
  - 성공(`SUCCESS`) / 불확실(`UNCERTAIN`) / 실패(`FAILED`) 상태가 올바르게 표시되는지 확인.
  - Zoom/Pan 조작 시 캔버스 좌표 정합성 유지.
  - **가드레일:** 병 외곽 검출 성공이 제품 정상 판정을 뜻하지 않으며, 내부 림 검출이 불확실하거나 실패한 경우 그 상태가 올바르게 표출된다면 정상 처리임.

#### 5. TC-12: 영역별 GV와 계산 불가 상태
- **구현 상태:** **구현 완료 / Chrome 회귀 자동화 대기** (`BottleEdgeDetails.tsx`)
- **위험도:** Level 1 (읽기 전용 UI)
- **주요 검증:**
  - 4대 영역 통계(평균, 중앙값, 표준편차, 픽셀 수, 면적 비율) 표시 확인:
    - **A 영역:** 전체 ROI
    - **B 영역:** 병 외곽 내부
    - **C 영역:** 내부 림 후보 내부
    - **D 영역:** 병 외곽 바깥 배경
  - **가드레일:** 내부 림의 닫힌 영역이 검출되지 않으면 C 영역 통계를 `계산 불가`로 표시하는 것이 정상 동작임.
  - **아키텍처 확인:** 영역별 GV는 브라우저 캔버스 기반 분석 결과이며 서버 최종 판정에 직접 관여하지 않음 (가상의 서버 `quality_metrics` API 단언 금지).
  - 전체 ROI 평균 GV 하한(125.0) 및 PatchCore 임계값(34.1442) 기준선 유지 확인.

### 3.2 Phase 2: 상태 변경 검사 E2E (별도 승인 단계)

Phase 2는 실제 Grab 캡처 생성, PatchCore 모델 CPU 추론, 재검사 그룹 생성, 수동 확인 레코드 추가 등 시스템 상태를 변경하는 시나리오입니다. 격리된 테스트 환경 및 사전 승인 하에 자동화합니다.

- **대상 시나리오:**
  - **TC-02:** 영상 Pause → ROI 선택 → Grab Crop 생성 (Level 2)
  - **TC-03:** 신규 정상 Capture에서 검사 버튼 활성화 확인 (Level 1, **단 TC-02의 신규 Capture 생성에 종속되므로 Phase 2에서 검증**)
  - **TC-04:** Grab 검사 완료 후 점수/품질/최종판정 표시 (Level 2)
  - **TC-05:** 같은 Capture 중복 검사 차단 및 새 제품 전환 (Level 2)
  - **TC-06:** 오래된 RIG·pending 상태 및 404 안전 복구 (Level 2)
  - **TC-09:** 검사 ID 일치 및 이전 결과 잔존 방지 (Level 1)

### 4.2 비현실적 기대 조건 배제 및 현실적 검증 기준

자동화 스크립트 작성 시 아래와 같은 비현실적 단언을 금지하고 현실적인 기준으로 검증합니다:

1. **이미지 디테일 복원 단언 금지:** 줌(Zoom) 확대는 픽셀 래스터를 확대할 뿐 원본에 없던 광학적 디테일이 복원되지 않습니다.
2. **내부 림 원형 폐곡선 강제 금지:** 내부 림은 조명 반사나 불량 형태로 인해 닫힌 원으로 검출되지 않을 수 있으며, 이때 `계산 불가` 상태로 처리되는 것이 올바른 동작입니다.
3. **Edge 성공 = 제품 정상 오류 방지:** Edge 검출은 기하학적 형상 분석일 뿐 제품의 결함 유무(OK/NG)를 판정하지 않습니다.
4. **특정 프레임 REINSPECT 고정 금지:** 영상 속 특정 프레임이 무조건 REINSPECT를 반환할 것이라고 단정하지 않습니다.
5. **임의의 10초 타임아웃 배제:** 로컬 CPU 추론 속도 및 렌더링 부하를 고려하여 현실적인 비동기 대기(`waitForSelector`, `toBeVisible({ timeout: 15000 })`)를 적용합니다.
6. **백엔드 외부 호출 통제 증명:** 브라우저 트래픽 검사만으로 백엔드 호출이 0회라고 단정하지 않고 서버 로그 카운터를 대조합니다.
7. **미검증 필드 단언 금지:** 존재하지 않는 가상의 API 응답 필드나 DOM 속성을 단언하지 않고, 확인되지 않은 세부 사항은 "Codex 구현 시 실제 코드 확인 필요"로 남깁니다.

### 4.3 실패 증거 수집(Artifacts Preservation) 체계

테스트 실패 시 원인 규명을 위해 `data/outputs/e2e-evidence/{timestamp}_{test_id}/` 디렉터리에 다음 증거를 자동 수집합니다:

1. **Full-page High-res Screenshot (`failure_fullpage.png`)**: 브라우저 뷰포트 전체의 고해상도 렌더링 결과.
2. **DOM Snapshot (`dom_tree.html`)**: 실패 시점의 전체 HTML DOM 구조 덤프.
3. **Network Archive (`network_trace.har`)**: 브라우저 레벨의 HTTP 요청/응답 헤더 및 페이로드.
4. **Browser Console Log (`browser_console.log`)**: 브라우저 JavaScript Uncaught Error 및 Warning 로그.
5. **Backend Audit Log Dump (`backend_audit.log`)**: 외부 API 호출 여부 및 백엔드 예외 로그 덤프.
