## 2. 세부 기술 문제 및 개선 과제 분석

---

### [이슈 1] 서버 메모리 기반 세션 관리와 재시작 시 권한 유실

#### 1. 현상
- FastAPI 서버를 재시작한 후, 브라우저에 이전에 캡처한 이미지나 검사 ID가 남아있음에도 불구하고 `[Grab]`이나 검사 조회를 실행하면 `401 Unauthorized` 또는 `404 CAPTURE_NOT_FOUND` 오류가 발생함.
- 디스크 상에는 영구 저장된 Crop PNG(`data/outputs/grab_inspection_inputs/IMG-GRAB-*.png`)가 물리적으로 온전히 존재함에도, 웹 API를 통해서는 접근할 수 없음.

#### 2. 원인 분석
- **확인된 사실:**
  - `backend/capture_store.py`의 `_sessions` 딕셔너리와 `_captures` 딕셔너리가 **프로세스 메모리 상의 파이썬 객체**로만 유지됨.
  - 브라우저 쿠키(`vision_capture_session`)에 유효한 세션 토큰이 있어도, 서버가 재시작되면 서버 측 `_sessions`가 빈 딕셔너리로 초기화되므로 `authorize(token, csrf)`가 즉시 실패함.
  - 새로 브라우저가 세션을 부트스트랩하면 새로운 `owner` 난수가 발행됨. 그러나 이미 생성된 Crop 매니페스트(`IMG-GRAB-*.json`) 내부의 `owner` 필드는 과거 세션의 난수를 가리키고 있으므로, `backend/grab_inspection.py`의 `authorize_record()`에서 소유자 불일치로 접근이 차단됨.
- **미확정 가설:** 없음 (코드 로직 상 100% 확인된 구조적 제약).

#### 3. 사용자에게 미치는 영향
- 개발 중 백엔드 코드를 수정하여 Uvicorn이 재시작되거나 발표 리허설 중 서버를 다시 띄웠을 때, 기존에 시연용으로 준비해 둔 Grab 프레임과 검사 화면이 먹통이 되어 재현이 불가능해짐.

#### 4. 기존 대응 및 수정 내용
- 프론트엔드 `App.tsx` 마운트 시 `ensureCaptureSession()`을 선제 호출하여 세션을 조기 자동 발급하고, 401 발생 시 1회 재시도하도록 래핑함.
- 영속 Crop 이미지와 임시 전체 프레임 Capture의 물리적 저장 경로를 분리함.

#### 5. 현재 상태
- **부분 해결 (Partially Resolved):** 세션이 살아있는 단일 실행 주기 동안은 완벽히 동작하나, 프로세스 재시작 시의 영속성 유지는 미해결 상태임.

#### 6. 임시 대응 방법 (Workaround)
- 발표 직전에는 백엔드 서버를 절대 재시작하지 않고 단일 프로세스를 유지함.
- 세션이 끊어졌을 경우, 기존 Grab 조회를 시도하지 않고 LiveView에서 비디오를 일시정지한 뒤 `[새 제품 검사 시작]` 버튼을 누르고 완전히 새로운 Grab을 1회 수행하여 새 세션에 바인딩함.

#### 7. 권장 근본 해결 방법 (Long-term Solution)
- **세션 저장소 영속화:** `_sessions`를 메모리 딕셔너리 대신 Redis 또는 PostgreSQL의 `user_sessions` 테이블에 저장하여 서버 재시작 후에도 토큰 유효성을 유지.
- **작업자 인증 기반 소유권 분리:** 임의의 브라우저 쿠키 난수(`owner`) 대신, 로그인된 작업자 ID(`operator_id`)와 RBAC 권한을 기준으로 Crop 파일 접근 인가를 수행하도록 아키텍처 개편.

#### 8. 관련 증거 및 테스트
- 관련 파일: `backend/capture_store.py:25-90`, `backend/grab_inspection.py:130-145`
- 테스트 기록: `tests/test_vision_judge.py`의 세션 재시작 합성 테스트(1 PASS) — 재시작 후 기존 쿠키 거부 및 영속 바이트 보존 검증 완료.

### [이슈 2] 임시 Capture 프레임의 30분 TTL과 서버 종료 시 파일 삭제

#### 1. 현상
- 캡처를 수행하고 시간이 30분 이상 경과하거나, FastAPI 서버를 정상 종료(Ctrl+C)했을 때 `data/outputs/captures/CAP-*.png` 파일이 디스크에서 자동으로 삭제됨.
- 반면 `data/outputs/grab_inspection_inputs/`의 Crop PNG와 `data/inspections.jsonl`은 삭제되지 않고 남아있어 파일 간 참조 불일치 우려 발생.

#### 2. 원인 분석
- **확인된 사실:**
  - `CaptureStore`의 `ttl_seconds` 기본값이 `1800` (30분)으로 설정되어 있어, `cleanup()` 실행 시 30분이 지난 임시 캡처는 `_remove()`를 통해 디스크에서 unlink됨.
  - `backend/main.py`의 lifespan 컨텍스트 종료 시 `captures.close()`를 호출하며, 이 함수는 관리 중인 모든 `CAP-*.png`를 삭제하고 프로세스를 끝냄 (`capture_store.py:224-228`).
  - 서버 시작 시 `_directory()` 역시 초기화 마커를 확인하며 디렉터리 내의 관리 대상을 전면 정리함.
- **미확정 가설:** 없음 (디스크 용량 고갈 방지를 위해 의도적으로 작성된 라이프사이클 정책임).

#### 3. 사용자에게 미치는 영향
- 시연 30분 전에 미리 프레임을 캡처해 두면 발표 시점에 이미 이미지가 증발해 404가 발생할 수 있음.
- 백엔드 프로세스가 종료되면 임시 원본 프레임이 사라져 사후 감사 시 전체 프레임 복원이 어려움.

#### 4. 기존 대응 및 수정 내용
- **영속 데이터와 임시 데이터의 엄격한 분리:** 검사에 투입되는 병 영역 Crop은 `grab_inspection_inputs`에 영구 보존하여 `CaptureStore.close()`가 지우지 못하도록 격리함.
- **오프라인 3중 백업 스크립트 구축:** `VisionInsight_GrabBackup_*` 디렉터리에 복사 전 원본, 복사 후 원본, 백업본의 SHA256 해시를 전수 검증하는 안전 백업 매뉴얼 수립 (`docs/day7-step11-capture-backup-plan.md`).

#### 5. 현재 상태
- **부분 해결 (Partially Resolved):** Crop과 검사 결과는 영구 보존되나, 1920×480 임시 Capture 원본은 여전히 수명이 제한됨.

#### 6. 임시 대응 방법 (Workaround)
- 발표 시작 10분 전에 LiveView에서 새로운 프레임을 Grab하여 30분 TTL 타이머를 갱신함.
- 서버를 재시작해야 할 경우, 사전에 PowerShell 스크립트로 `captures` 폴더를 외부 디렉터리로 복사 백업함.

#### 7. 권장 근본 해결 방법 (Long-term Solution)
- 산업용 NVR(Network Video Recorder) 아키텍처를 도입하여, 임시 폴더 삭제 방식 대신 콜드 스토리지(GCS / S3)로 자동 아카이빙되는 롤링 정책으로 전환.

### [이슈 3] 브라우저 상태(localStorage) 잔존으로 인한 검사 버튼 비활성화

#### 1. 현상
- 사용자가 새로운 프레임을 Grab했음에도 불구하고 우측 패널의 `[Grab 이미지 검사]` 버튼이 비활성화(Disabled)되어 클릭할 수 없음.
- 화면에 `재검사 한도 도달` 또는 `동일 제품 재검사 확인 필요`라는 경고 문구가 표시됨.

#### 2. 원인 분석
- **확인된 사실:**
  - 프론트엔드가 이전 검사에서 발급받은 재검사 그룹 ID(`reinspection_group_id`)를 브라우저의 `localStorage` (`group_hint_key`)에 캐싱해 둠.
  - 이전 검사가 3회 재검사를 모두 소진했거나(`MANUAL_REVIEW_REQUIRED`), `RETRY_ALLOWED` 상태일 때, 프론트엔드 검증 함수 `canUseCapture`와 `grabInspectionDisabled`가 안전 규칙에 따라 신규 검사를 차단함.
  - 사용자는 새로운 병을 검사하려고 하는데, 시스템은 이전 병의 4번째 불법 재검사로 인식한 것임.
- **미확정 가설:** 없음.

#### 3. 사용자에게 미치는 영향
- 시연자가 새 병을 검사하려 할 때 버튼이 눌리지 않아 시스템이 멈춘 것처럼 보이는 치명적인 UX 병목 발생.

#### 4. 기존 대응 및 수정 내용
- `GrabInspectionPanel.tsx`에 **`[새 제품 검사 시작]`** 버튼을 신설함.
- 이 버튼 클릭 시 브라우저 캐시(`localStorage`)의 그룹 힌트를 초기화하고 서버에 새 캡처 상태를 조회하여 즉시 최초 검사 대기 상태로 전환되도록 복구 경로를 구현함 (`docs/day7-step8-1-industrial-reinspection-ux.md`).

#### 5. 현재 상태
- **해결 완료 (Resolved):** 작업자가 새 제품 검사 시작 버튼을 누르면 정상적으로 버튼이 활성화됨.

#### 6. 임시 대응 방법 (Workaround)
- 버튼이 비활성화되어 있으면 즉시 `[새 제품 검사 시작]`을 누르고 확인 팝업창에서 '확인'을 클릭함.

### [이슈 4] MVTec 스튜디오 기준(125.0)과 LiveView 영상 배경의 조도 판정 불일치

#### 1. 현상
- 컨베이어 벨트 영상(`VID-000001`)에서 병을 정상적으로 Crop하여 검사하면, 실제 병에 아무런 결함이 없고 육안상 선명하게 보여도 평균 밝기가 항상 **57.0 ~ 59.8** 수준으로 측정됨.
- 시스템의 정상 밝기 하한선인 **125.0**에 크게 미달하여 모든 Grab 검사가 예외 없이 **`REINSPECT (IMAGE_QUALITY_WARNING)`**로 판정됨 (`INSP-001652`, `INSP-001669` 등 전수 발생).

#### 2. 원인 분석
- **확인된 사실:**
  - `BRIGHTNESS_LOW_THRESHOLD=125.0` 기준치는 깨끗한 백색 스튜디오 조명 아래에서 촬영된 MVTec AD Bottle 정적 학습 데이터셋(`mean = 136.34`)의 통계에 기반하여 설정됨 (`docs/baseline_brightness_statistics.md`).
  - 반면 LiveView 영상은 컨베이어 벨트와 공장 배경이 어두운 회색/검은색 톤으로 구성되어 있음.
  - `backend/vision.py`의 조도 계산 로직은 Crop된 291×278 이미지의 **모든 픽셀(병 본체 + 주변 어두운 배경)의 단순 산술 평균**을 구함.
  - 따라서 병 유리 표면이 정상이어도 주변 어두운 배경 영역의 픽셀값(GV 20~40)이 전체 평균을 57대로 끌어내림.
- **미확정 가설:**
  - "공장 현장 조명 장치에 물리적 고장이 발생했다"는 가설은 시스템 로그의 추정일 뿐, 실제 물리적 원인(조명 강도 저하 vs 카메라 셔터 스피드/게인 노출 부족 vs 배경 비율 과다)은 현재 소프트웨어 지표만으로 확정할 수 없음 (UNKNOWN).

#### 3. 사용자에게 미치는 영향
- 데모 시연 시 아무리 정상 병을 캡처해도 결코 `OK` 배지가 나오지 않고 항상 주황색 `REINSPECT` 배지가 출력되어 시스템 오작동으로 오해받을 수 있음.

#### 4. 기존 대응 및 수정 내용
- **결정론적 판정 가드레일 정립:** 조도가 어두울 때 모델이 NG를 내더라도 억울한 폐기를 막기 위해 `REINSPECT`를 우선 적용하는 우선순위 규칙(`decision.py`)을 확립함.
- AGENTS.md 규칙 7에 따라 "낮은 밝기는 관측 사실이나, 조명 고장으로 단정하지 않는다"는 가이드라인을 문서와 UI에 공식 반영함.
- UI에 `평균 GV (ROI 전체): 57.41`과 함께 기준치(125.0)를 명시하여 사용자가 수치적 이유를 알 수 있도록 개선함.

#### 5. 현재 상태
- **부분 해결 (Partially Resolved):** 공정 안전 규칙은 완비되었으나, 배경 노이즈로 인한 저조도 오경보는 여전히 발생함.

#### 6. 임시 대응 방법 (Workaround)
- 발표 시 이를 시스템 결함으로 변명하지 않고, **"조도가 불확실할 때 정상/불량을 섣불리 단정하지 않고 작업자 재검사로 돌리는 머신비전 안전 철학의 실제 증거"**로 프레이밍하여 설명함.

#### 7. 권장 근본 해결 방법 (Long-term Solution)
- **전경/배경 분할(Otsu Thresholding / Masking):** Crop 이미지 전체를 평균 내지 않고, Otsu 알고리즘이나 모폴로지 연산으로 어두운 컨베이어 배경을 마스킹 제외한 뒤 **순수 병 본체 영역의 픽셀만 평균을 계산**하도록 알고리즘 고도화.
- **Grab 전용 조도 프로파일 분리:** 정적 MVTec 이미지용 임계값(125.0)과 컨베이어 실시간 비디오용 임계값(예: 50.0)을 환경설정(`config.py`)에서 소스별로 분리 정의.

### [이슈 5] PatchCore 모델의 결함 미검출 한계 (Recall 50.79%)와 전처리 불일치

#### 1. 현상
- 공식 MVTec Bottle 테스트 세트 83장 평가 시, 정밀도(Precision)는 100%였으나 재현율(Recall)은 **50.79%**에 머물러 실제 결함 63건 중 31건을 미탐(False Negative)함.
- 특히 T06 시나리오(`IMG-BOTTLE-0001`, 미세 오염)에서 실제 결함 병임에도 이상 점수가 `12.9806` (또는 `32.2679`)로 고정 임계값 `34.1442`보다 낮아 모델 소견이 `OK`로 판정됨.

#### 2. 원인 분석
- **확인된 사실:**
  - PatchCore 백본(ResNet-18)은 256×256 패치 임베딩을 기반으로 하므로, 1~2픽셀 두께의 미세한 스크래치나 투명 오염은 정상 배경 패치와의 유클리드 거리 상에서 뚜렷한 이상치로 두드러지지 못함.
  - **전처리 이중 정규화(Double Normalization) 발견:** 외부 래퍼(`patchcore_inferencer.py`)에서 `transforms.Normalize`를 1회 적용하고, 모델 내부 체크포인트에서 동일 정규화가 또 적용되어 텐서 입력값이 $[-11.37, +9.93]$로 왜곡됨 (`docs/day5-step3-phaseb2a-patchcore-preprocessing-audit.md`).
  - 고정 임계값 `34.1442`는 이 2회 정규화가 적용된 수치 공간에서 산출된 것임. 단일 정규화로 수정 시 이상 점수가 11~63% 급락하여 기존 임계값이 완전히 무력화됨을 A/B 테스트로 증명함.
- **미확정 가설:**
  - "단순히 임계값을 34.1442에서 25.0으로 낮추면 해결될 것이다"라는 가설은 위험함. 독립 검증셋 통계($\mu + 3\sigma$)를 위배하여 정상 병에 대한 위양성(False Alarm)이 급증할 우려가 큼.

#### 3. 사용자에게 미치는 영향
- 미세 결함 병이 불량으로 분류되지 않고 합격 처리될 수 있는 품질 유출 리스크 존재.

#### 4. 기존 대응 및 수정 내용
- **엔지니어링 절제 및 동결 (Deferred):** 발표를 앞두고 임의로 임계값을 바꾸거나 체크포인트를 손대는 것은 회귀 위험이 너무 크므로, 현행 2회 정규화 코드를 보존하고 공식 기술 부채로 기록함 (`docs/visioninsight-patchcore-ab-deferred-handoff.md`).
- T06 검사를 "모델의 한계 사례"로 정직하게 고지하고, 테스트 Fixture Mock 데이터(Score 45.0)와 명확히 분리함.

#### 5. 현재 상태
- **미해결 기술 부채 (Deferred):** 모델과 임계값은 동결 상태임.

#### 6. 권장 근본 해결 방법 (Long-term Solution)
- **OpenCV 기하 룰 기반 검사 결합:** 병 입구 림(Rim)의 진원도($4\pi A/P^2$)와 동심도를 직접 계산하는 룰 기반 알고리즘을 딥러닝과 하이브리드로 결합 (`scripts/experiments/opencv_rim_inspection.py`).
- **전처리 단일화 및 Threshold 재보정:** 전체 데이터셋을 재전처리하여 단일 정규화 공간에서 Coreset 메모리 뱅크를 재구축하고 임계값을 재산출.

### [이슈 7] UI의 평균 GV 표시 누락 및 검사 상태 누수 문제

#### 1. 현상

- **확인된 사실:**
  - 프론트엔드 컴포넌트가 `metrics.mean` 프로퍼티를 직접 렌더링하지 않고 텍스트 상태 문자열만 바인딩하고 있었음.
  - 전역 상태 관리에서 `inspectionId`가 변경될 때 이전 Canvas의 오버레이 버퍼를 즉시 비우지 않아 비동기 렌더링 경합이 발생함.
- **미확정 가설:** 없음.

#### 3. 사용자에게 미치는 영향
- 검사 신뢰성에 의문이 생기고, 서로 다른 병의 결함 히트맵이 섞여 보이는 시각적 오류 발생.

#### 4. 기존 대응 및 수정 내용
- `frontend/src/utils/inspectionQualitySummary.ts` 모듈을 신설하여 `평균 GV (ROI 전체): {qualitySummary.meanLabel}`과 조도 기준(125.0)을 카드 상단에 명시적으로 출력하도록 수정함.
- `ImageView.tsx`와 `App.tsx`에서 탭 전환 및 신규 검사 트리거 시 `onSelectionStart()`를 통해 고유 `requestVersion` 에포크를 증가시켜 이전 이미지의 비동기 응답이 현재 화면을 오염시키지 못하도록 차단함 (`docs/day7-step11-real-inspection-ui-flow.md`).

#### 5. 현재 상태
- **해결 완료 (Resolved):** 평균 GV 수치가 선명하게 표시되며 이미지 간 상태 누수가 완벽히 차단됨.

## 3. 우선순위별 개선 과제 로드맵 (Roadmap)

시스템의 안정성과 완성도를 극대화하기 위해 이슈들을 3단계 우선순위로 구조화합니다.

```

│                        개선 과제 3단계 로드맵                          │

│   • 정적 프리셋 숏컷([T03:Warn]) 기반 100% 안전 시연 확보              │

│  [P1: 반복 검사 및 안정성]                                            │

│  [P2: 성능 및 구조 고도화]                                            │
│   • 컨베이어 센서 트리거 기반 완전 자동(AUTO) PLC 검사 연결            │
│   • Cloud Run 컨테이너 패키징 및 Google Cloud Storage(GCS) 연동       │
│   • 전처리 단일화 및 MVTec 전수 데이터 기반 Threshold Recalibration    │
```

### [P0: 내일 발표 및 실제 이미지 검사에 영향을 주는 과제]
1. **서버 세션 안정성 유지:** 발표가 끝날 때까지 Uvicorn 서버를 임의로 껐다 켜지 않고 단일 세션을 보존하여 `401 Unauthorized`를 원천 방어.
2. **검증된 UI 경로 준수:** 존재하지 않는 `Execution Logs` 아코디언 등을 시연하지 않고, 실제 구현된 `[Grab (Crop 반영)]` $\rightarrow$ `[Grab 이미지 검사]` 절차만 준수.
3. **비상 시연 경로 숙지:** 세션 장애 발생 시 즉시 `[Static Image]` 탭의 `[T03:Warn]` 프리셋으로 전환하여 조도 판정 원리를 매끄럽게 설명.

### [P1: 반복 검사 안정성과 데이터 접근·보존 과제]
1. **조도 평가 알고리즘 개선:** 전체 ROI 평균 대신 Otsu 전경 분할을 적용하여 어두운 컨베이어 배경 픽셀을 제외한 순수 병 영역 조도 계산.
2. **세션 저장소의 외부화:** FastAPI 인메모리 세션을 DB/Redis로 이관하여 서버 재시작 후에도 기존 세션과 검사 소유권을 온전히 복원.
3. **OpenCV 기하 검사 통합:** 딥러닝이 놓치는 병 입구 림(Rim) 결함을 잡기 위해 `opencv_rim_inspection.py`를 정식 검사 파이프라인으로 결합.

### [P2: 성능 개선 및 향후 구조 고도화 과제]
1. **완전 자동(AUTO) 파이프라인 구현:** 광전 센서 하드웨어 트리거 신호 수신 시 PostgreSQL의 Active ROI를 자동 슬라이싱하여 추론하고 PLC 배출기를 구동하는 실시간 제어 체계 구축.
2. **클라우드 인프라 배포:** Google Cloud Run 컨테이너화 및 Cloud Storage 영구 저장소 연동.
3. **PatchCore 전처리 단일화:** 이중 정규화 기술 부채를 해결하기 위해 전처리 단일화 후 전체 정상 데이터셋으로 고정 임계값 재산출.
