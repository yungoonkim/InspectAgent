### Q1. 개발 과정에서 가장 어려웠던 부분은 무엇인가?
**답변 요약:** "단순히 모델 API를 호출하는 것보다, 외부 LLM의 불확실한 통신을 제어하고 검증 가능하며 안전한 엔지니어링 가드레일을 구축하는 과정에 가장 많은 분석과 재검증이 집중되었습니다."  
**상세 답변:**  
AI 모델을 연동하는 프로토타입 제작 자체보다, 산업 현장에서 신뢰할 수 있는 수준의 Agent를 만들기 위한 다음 3대 기술 난제 해결에 엔지니어링 노력이 집중되었습니다:
1. **구조화 출력 호환성 (HTTP 400):** 복잡한 Pydantic 스키마 직접 전송 시 발생하는 서버 거부를 극복하기 위해, 단순 JSON 전송 및 서버 Python 변환/검증이라는 2단계 아키텍처를 수립했습니다.
2. **최종 응답 지연 및 타임아웃 (HTTP 504):** 도구 조사와 최종 JSON 생성의 부하 차이를 계측하여 요청 단계별 timeout을 분리하고 실제 HTTP 전파 동작을 검증했습니다.
3. **ERROR 시나리오 근거 검증 공백:** T05 영상 로드 실패 오프라인 검증에서 발견된 오류 로그 미조회 및 미측정값 누락, SKIPPED 상태만으로 모델 장애를 단정하는 비약 위험을 차단하기 위해 17개 필수 사실 정책과 회귀 테스트를 구축했습니다.  
특정 작업의 소요 시간을 자의적으로 단정할 수는 없으나, "모델의 생성 결과를 서버가 어떻게 안전하게 검증하고 거부할 것인가"를 정의하는 데 가장 많은 검증이 수반되었습니다.

### Q2. Gemini가 보고서를 작성하는데 왜 별도 Python 검증이 필요한가?
**답변 요약:** "LLM은 확률적 텍스트 생성기이며, 제조 현장이 요구하는 결정론적 정합성과 안전 규칙을 스스로 보장하지 못하므로 '형식적으로 유효한 JSON'과 '실제 근거를 충족한 안전한 보고서'를 엄격히 분리하기 위함입니다."  
**상세 답변:**  
Gemini가 문법적으로 완벽한 JSON을 생성하더라도 산업 현장에서는 다음과 같은 중대한 안전 위험이 발생할 수 있습니다:
1. 실제로 도구를 호출하여 확인하지 않은 값을 그럴듯하게 지어내는 환각(Hallucination)
2. 서버 메모리에 기록된 실제 검사 지표(조도, 이상 점수 등)와 다른 수치 기재
3. 서버 비즈니스 규칙이 이미 확정한 최종 판정(`final_result`)을 모델이 임의로 번복
4. 근거 사실(`evidence_refs`)이 없는 위험한 현장 조치 권고  
따라서 VisionInsight는 **'모델을 맹신하지 않고 서버가 엄격히 검증한다'**는 원칙하에, Python 서버 계층에서 도구 실행 영수증(`Evidence ID`), JSON Pointer(`RFC 6901`), 판정 불변성 가드레일을 통해 1:1 결정적 검증을 수행하며, 불일치 시 `EVIDENCE_MISMATCH`(HTTP 502)로 즉시 거부합니다.

### Q3. HTTP 400은 어떤 스키마 속성 때문에 발생했는가?
**답변 요약:** "여러 형태의 단순 스키마와 복잡한 스키마를 비교 검증하여 복잡한 스키마에서 오류를 재현했으나, 정확하게 어떤 Pydantic 속성이 Gemini 서버의 거부를 유발했는지는 외부에서 관측할 수 없어 **UNKNOWN**입니다."  
**상세 답변:**  
초기 `DiagnosisDraft`의 중첩된 Pydantic 모델을 Gemini의 `response_json_schema`로 직접 전달했을 때 HTTP 400 ClientError가 발생했습니다.  
엔지니어링 과정에서 스키마 복잡도별 비교 검증을 수행하여 단순한 형태의 JSON 스키마는 정상 수락되고 복잡한 스키마에서 거부가 발생함을 확인했으나, Google API 서버 내부의 스키마 파서 구현을 직접 열람할 수 없으므로 특정 속성(예: anyOf, $defs 참조, nullable 등)을 확정적 원인으로 단정하지 않고 **UNKNOWN**으로 기록했습니다.  
해결책으로 원인을 추측하여 스키마를 억지로 끼워맞추는 대신, Gemini에는 단순 JSON 스키마만 전달하고 서버가 토큰 카탈로그를 주입한 뒤, 수신된 결과를 서버 Python에서 `DiagnosisDraft`로 변환하여 Pydantic 및 Evidence 검증을 거치는 안정적인 우회 아키텍처를 확립했습니다.

### Q4. HTTP 504는 30초 timeout으로 완전히 해결된 것인가?
**답변 요약:** "완전한 해결책이 아니며, 실험 회차에서 최종 요청 timeout을 30초로 설정하여 18.967초에 성공(전체 E2E 24.600초 PASS)한 단일 실측치일 뿐 향후 반복 안정성을 보증하지는 않습니다."  
**상세 답변:**  
과거 T03 검증 시 15초 timeout에서 약 14.154초 소요 후 HTTP 504(DEADLINE_EXCEEDED)가 발생했으나, Google 서버 내부 큐 적체나 네트워크 지연 등의 근본 원인은 외부에서 알 수 없었습니다(UNKNOWN).  
조사 도구 호출(2~3초)과 최종 생성 요청의 연산 부하가 다름을 계측으로 확인한 뒤, 전체 60초 예산을 유지하면서 실험 회차(`t03_operational_final30_1`)에서 최종 요청에만 30초 timeout을 선택 적용했습니다.  
그 결과 최종 요청은 **18.967초** 만에 HTTP 200을 수신했고 전체 E2E는 **24.600초**에 완전 성공(PASS)했습니다.  
하지만 운영 기본 timeout은 여전히 15초이며, 30초 설정이 과거 504의 유일한 원인을 영구히 해결했다고 볼 수 없습니다. 부하 상황에 대비하기 위해 향후 프롬프트 경량화, 비동기 작업 큐 도입, 장기적 반복 계측이 수반되어야 합니다.

### Q5. T05의 실제 실서버 E2E 검증 결과와 현재 상태는 무엇인가?
**답변 요약:** "T05는 기존 실서버 E2E 1회차에서 두 필수 도구 성공 후 3차 후속 조사에서 HTTP 504가 발생하여 1회 FAIL을 기록했습니다. 이후 불필요 조사를 방지하는 조기 종료 정책을 구현하여 오프라인 Mock 회귀 테스트(984 PASS)를 마쳤으며, 개선 이후 실제 Gemini API 재검증을 대기하고 있는 상태입니다."  
**상세 답변:**  
T05(IMAGE_LOAD_FAILED 영상 로드 실패 시나리오)는 실제 실서버 검증(`INSP-001405`, `t05_operational_final30_1`)에서 두 필수 도구(`get_inspection_result`, `get_execution_logs`) 실행에 성공하고 실제 오류 이벤트(`IMAGE_LOAD_FAILED`, `INSPECTION_FAILED`) 및 17개 원천 근거를 모두 확보했습니다.  
그러나 이미 충분한 오류 근거가 확보되었음에도 모델이 3번째 후속 조사를 요청하다가 HTTP 504(서버 내부 원인 UNKNOWN)가 발생하여 최종 JSON 보고서를 완성하지 못하고 FastAPI 502로 1회 실패(FAIL)했습니다.  
이에 이미지 로드 실패 전용 조사 조기 종료 정책을 구현하여 필수 도구와 이벤트가 확보되면 즉시 최종 JSON 보고서로 전환되도록 보완하고 계측기 WARNING 오분류를 정정했습니다.  
오프라인 Mock 테스트에서 조사 2회 후 즉시 최종 보고서 전환에 성공하여 전체 984개 pytest를 전원 통과했으나, 개선 이후 실제 Gemini API 재검증은 아직 수행하지 않았으므로 **오프라인 Mock PASS / 실서버 개선 후 재검증 대기** 상태로 정확히 구분하여 보고합니다.

### Q6. 이런 복잡한 Agent 검증 구조가 실제로 필요한 이유는 무엇인가?
**답변 요약:** "산업 제조 현장은 오판이나 허위 정보가 생산 라인 정지나 불량품 유출 등 막대한 경제적 손실로 이어지는 고위험 도메인이기 때문입니다."  
**상세 답변:**  
일반적인 대화형 AI에서는 그럴듯한 답변이 허용될 수 있지만, 공장 환경에서는 다음 세 가지가 필수적입니다:
1. **추적성 (Auditability):** 이 보고서의 수치가 실제 몇 번 검사의 어떤 도구에서 나왔는지 영수증(Evidence ID)으로 증명되어야 합니다.
2. **불변성 (Invariance):** 안전 및 규정상 서버 규칙이 내린 최종 판정(OK/NG/REINSPECT)을 사후 분석 AI가 절대 번복해서는 안 됩니다.
3. **거부 능력 (Safe Rejection):** 필수 근거(예: T05의 오류 로그)가 누락되었을 때 그럴듯한 보고서를 만드는 대신 즉시 `EVIDENCE_MISMATCH`로 보고서를 거부할 수 있어야 합니다.  
따라서 단순 JSON 유효성을 넘어 실제 현장 팩트에 근거한 안전성을 담보하기 위해 결정적 검증 구조가 반드시 필요합니다.

### Q7. Gemini 대신 Codex가 Agent 코드를 작성한 이유는 무엇인가?
**답변 요약:** "두 모델의 절대적인 성능 우열에 따른 것이 아니라, IDE 개발 엔지니어링 도구와 런타임 비즈니스 추론 Agent라는 역할 분담에 따른 선택입니다."  
**상세 답변:**  
- **Codex (개발 엔지니어링 도구):** 개발자 환경(IDE)과 터미널에 밀접하게 통합되어 파일 수정, 단위 테스트 실행, 정적 분석 및 리팩토링 등 **소프트웨어 개발 작업**에 특화되어 사용되었습니다.
- **Gemini (런타임 비즈니스 추론 Agent):** 실제 검사 서비스가 기동 중일 때 FastAPI와 통신하며 Function Calling으로 도구를 제안하고, 산업 검사 데이터를 사후 분석하여 작업자 보고서를 생성하는 **런타임 AI Agent**로 사용되었습니다.  
중요하게도, Gemini가 코딩을 수행했더라도 HTTP 400(서버 스키마 제약)이나 HTTP 504(외부 네트워크/서버 지연) 문제는 동일하게 발생했을 네트워크 및 API 수준의 엔지니어링 과제입니다. 따라서 이를 특정 모델의 코딩 우위로 설명하지 않으며, 각자의 환경에 최적화된 도구로 분리 운용한 것입니다.

### Q8. 수많은 비전 모델 중 왜 PatchCore를 선택했습니까?
**답변 요약:** "정상 데이터만으로 학습 가능하며, 국소 결함 위치 파악 능력이 뛰어나고 CPU 추론에 적합하기 때문입니다."  
**상세 답변:**  
제조 라인에서는 양품에 비해 불량 데이터가 극히 희귀하고 불량의 형태도 사전에 정의하기 어렵습니다. 따라서 지도 학습(Classification/YOLO) 대신 비지도 이상 탐지(Anomaly Detection)가 필수적입니다.  
비지도 모델 중 AutoEncoder나 GAN 계열은 블러 현상(Blurry reconstruction)으로 인해 미세 결함을 복원해 버리는 한계가 있습니다. 반면 PatchCore는 사전 학습된 CNN(ResNet-18)의 중간 레이어 특징 맵을 메모리 뱅크에 보관하고 최근접 이웃(Nearest Neighbor) 거리로 이상을 계산하므로, 미세한 스크래치나 오염의 국소적 특징을 가장 잘 보존합니다. 또한 Coreset 서브샘플링을 통해 메모리 뱅크를 경량화하면 CPU 환경에서도 40ms 초반의 실시간 추론이 가능하기 때문에 산업용 엣지 환경에 적합하다고 판단했습니다.

### Q9. 비지도 학습 모델(Anomaly Detection)의 장단점은 무엇입니까?
**답변 요약:** "장점은 미지의 결함 탐지와 라벨링 비용 제로, 단점은 과탐/미탐 제어의 난이도와 임계값 민감성입니다."  
**상세 답변:**  
- **장점:** 불량 이미지 수집과 픽셀 단위 라벨링(Ground Truth 마스킹) 비용이 전혀 들지 않으며, 과거에 한 번도 발생한 적 없는 완전히 새로운 유형의 결함(미지의 불량)도 정상 패턴과의 거리 차이로 탐지해 낼 수 있습니다.  
- **단점:** 정상 제품의 자연스러운 공정 편차(예: 병 성형 시의 미세한 유리 두께 차이나 반사광)를 결함으로 오인(False Positive)하거나, 배경과 대비가 낮은 미세 오염을 정상으로 놓치는(False Negative) 미탐이 발생하기 쉽습니다. 따라서 정교한 임계값 설정과 영상 품질 분석의 분리가 필수적입니다.

### Q10. 공식 판정 임계값(34.1442)은 어떻게 결정되었습니까? (학습 이미지 수는 몇 장인가?)
**답변 요약:** "정상 이미지 180장으로 PatchCore 메모리 뱅크를 학습하고, 별도로 완전히 격리된 독립 정상 검증 데이터 29장의 이상 점수 분포에 통계적 $\mu + 3\sigma$ 원칙을 적용하여 34.1442를 도출했습니다."  
**상세 답변:**

### Q15. Gemini는 Python 도구를 어떻게 실행합니까? (sandbox 여부)
**답변 요약:** "Gemini는 Function Calling으로 조회 도구명과 인자를 제안할 뿐이며, FastAPI AgentService가 호출 유효성을 검증한 뒤 허용된 Python 조회 도구를 서버 내부에서 실행합니다. 별도의 독립 sandbox 가동은 아닙니다."  
**상세 답변:**  
SDK의 자동 함수 실행을 비활성화하고 수동 오케스트레이션을 구현했습니다.  
1. Gemini에게 검사 ID와 4대 조회 도구 선언을 전달합니다.  
2. Gemini가 `get_inspection_result(inspection_id=...)` 형태의 Function Call 제안을 반환합니다.  
3. FastAPI AgentService가 도구명 허용 여부, Pydantic 인자 유효성, 고정 검사 ID 일치성을 엄격히 검증합니다.  
4. 검증을 통과한 호출에 한해 서버의 스레드풀에서 실제 로컬 Python 도구를 실행하고, JSONL 저장소에서 데이터를 안전하게 읽어옵니다.  
5. 서버는 실행 결과에 고유한 `Evidence ID`(E0001 등)를 부여하고, 이를 `role="user"`의 `FunctionResponse` 형태로 Gemini에게 돌려줍니다.

### Q16. 서버의 Evidence 검증은 무엇을 보장합니까?
**답변 요약:** "도구 실행 영수증인 Evidence ID와 RFC 6901 JSON Pointer를 통해, 모델이 보고서에 작성한 관측 사실이 서버 메모리의 실제 도구 결과와 1:1 결정적으로 일치함을 보장합니다. 단, 모든 자연어 가설이나 미래 출력을 100% 완전 검증한다고 보장하는 것은 아닙니다."  
**상세 답변:**  
Gemini가 보고서에서 관측 사실(`observed_facts`)을 작성할 때, 반드시 다음 요소를 명시해야 합니다:
1. `evidence_id`: 실제 성공한 도구 실행 영수증 ID (예: `E0001`, `E0002`)
2. `source_tool`: 호출한 도구명 (예: `get_inspection_result`, `analyze_image_quality`)
3. `source_field`: 데이터 내의 정확한 JSON Pointer (예: `/data/final_result`, `/data/metrics/mean`)
4. `observed_value`: 모델이 관측했다고 주장하는 값 (예: `"REINSPECT"`, `81.24`)  
서버는 파이썬 메모리에서 실제 도구 실행 결과와 1:1 비교하여 검증 대상 필드가 정확히 일치하지 않으면 보고서 전체를 즉시 거부(`EVIDENCE_MISMATCH` / HTTP 502)합니다. 실제 실서버 검증에서 T01 6개 사실과 T03 12개 사실이 이 검증을 통과했습니다.
