## 🎙️ 실전 발표 대본 (구어체)

### 1. 인트로 및 검사 개요 (0:00 ~ 0:20)
> "화면에 보시는 것은 실제 개발 환경에서 실서버 Gemini E2E 검증을 통과한 **T03 조도 경고 시나리오(`INSP-001398`)의 인터랙티브 데모 화면**입니다.  
> 
> 상단 주황색 배너에 명시되어 있듯이, 본 화면은 네트워크 장애나 과금 위험을 원천 차단하기 위해 **실제 서버에 기록된 정제 데이터를 재생하는 발표용 정적 데모**이며 현재 외부 Gemini API를 직접 호출하지 않습니다.  
> 
> 좌측 상단의 캔버스는 실제 검사 이미지가 아닌 **규격 및 조도 통계 참고용 개념도**입니다.  
> 이미지 검사 결과 평균 밝기가 **81.24**, 표준편차 **55.79**로 측정되어 영상 품질에 **`WARNING_LOW_BRIGHTNESS`** 조도 저하 경고가 감지되었습니다."

### 2. PatchCore 임계값과 모델 판정 (0:20 ~ 0:40)
*(상단 네비게이션에서 **[1. PatchCore 검사]** 칩을 클릭합니다)*

> "화면 중앙의 PatchCore 이상치 탐지 게이지를 보시겠습니다.  
> 게이지의 0부터 50은 시각화를 위한 **표시 눈금**입니다.  
> 모델이 산출한 이상 점수(Anomaly Score)는 **31.7779**로, 고정 임계값 **34.1442**보다 낮아 **PatchCore 모델 자체는 OK(양품)로 판정**했습니다. CPU 추론에는 **42.72ms**가 소요되었습니다.  
> 
> 하지만 조도가 심각하게 떨어진 비정상 환경에서 촬영되었기 때문에, 모델의 OK 판정만으로는 실제 결함 여부를 신뢰할 수 없습니다.  
> 따라서 시스템은 규칙 기반 판정 신뢰도를 즉시 **`UNCERTAIN_DUE_TO_IMAGE_QUALITY`**로 하향 조정했습니다."

### 3. 서버 규칙 기반 최종 판정 (REINSPECT) (0:40 ~ 1:00)
*(상단 네비게이션에서 **[2. 판정 규칙]** 칩을 클릭합니다)*

> "바로 아래의 서버 최종 판정 계층을 주목해 주십시오.  
> T01의 초록색 OK 배지와 달리, 여기서는 **주황색 `REINSPECT(재검사 필요)` 배지**가 부여되었습니다.  
> 
> FastAPI 서버의 6대 우선순위 집계 규칙 중 **'Rule 2'**가 발동하여, 최종 사유 코드 **`IMAGE_QUALITY_WARNING`**과 함께 최종 판정을 **`REINSPECT`**로 확정했습니다.  
> 모델 판정은 OK였지만 영상 품질 경고를 반영하여 서버가 최종 판정을 재검사 필요 상태로 안전하게 분류한 것입니다.  
> 
> 여기서 중요한 점은, 현재 구현의 `REINSPECT`는 서버의 최종 검사 판정값이며 **실제 공장의 물리적인 선별이나 배출기 제어를 수행한 것은 아니라는 점**입니다. 아울러 이 판정은 서버의 확정 판정이며 뒤이어 실행되는 Gemini Agent가 변경할 수 없습니다."

## 💡 발표자 Q&A 원포인트 팁

- **Q: 이전 T03 테스트에서는 왜 HTTP 504가 발생했나요?**  
  **A:** "이전 T03 검증에서는 최종 JSON 생성 요청이 약 14.15초 후 HTTP 504(FastAPI 응답: HTTP 502)로 실패했습니다. 당시 요청 timeout은 15초였지만, 정확한 서버 내부 원인은 확인되지 않았습니다(UNKNOWN). 이후 최종 JSON 요청에만 30초 timeout을 적용한 단일 재검증(`t03_operational_final30_1`)에서는 약 18.97초(18.967초) 후 HTTP 200을 받아 전체 분석이 성공했습니다. 다만 이 결과만으로 기존 504의 원인을 확정하거나 향후 안정성을 보장할 수는 없으며, 서버 내부의 절대적인 deadline은 관측할 수 없습니다(NOT OBSERVABLE)."

- **Q: Gemini가 제품을 REINSPECT로 판정하고 불량 라인으로 배출한 것인가요?**  
  **A:** "아닙니다. REINSPECT 판정은 FastAPI 서버가 영상 품질 경고(`WARNING_LOW_BRIGHTNESS`)를 감지하고 6대 우선순위 집계 규칙 중 'Rule 2'를 적용하여 내린 서버의 최종 검사 판정값입니다. Gemini는 이 결과를 사후에 도구로 조회하여 현장 작업자에게 재검사 권고와 추정 가설을 설명하는 진단 보조 역할을 수행할 뿐이며, 검사 판정을 변경할 권한이 없습니다. 또한 현재 프로토타입은 실제 공장의 물리적인 제품 선별이나 배출기 제어를 수행하지 않습니다."

- **Q: 조명 장치가 실제로 고장난 것인가요?**  
  **A:** "확인되지 않았습니다. 관측된 것은 이미지 밝기가 81.24로 낮아졌다는 통계적 사실뿐입니다. 조명 기구 자체의 물리적 고장인지, 작업장 환경광 변화인지, 혹은 카메라 노출값 문제인지는 검사 데이터만으로 확정할 수 없으므로, Agent 역시 '물리적 고장은 확인되지 않았다'는 제한을 붙여 가설 수준으로 제시하고 있습니다."

- **Q: 당시 밝기 판단 기준이 왜 `NOT_RECORDED`로 표시되나요?**  
  **A:** "검사 당시 서버의 품질 평가기가 경고(`WARNING_LOW_BRIGHTNESS`) 판정 결과와 평균·표준편차 실측치는 저장했으나, 판정에 사용된 상·하한 기준 임계값 필드를 데이터베이스에 명시적으로 기록하지 않았기 때문입니다. 저희 시스템은 추측으로 기준값을 채워 넣지 않고, 데이터의 정직성을 지키기 위해 실제 저장 상태 그대로 `NOT_RECORDED`로 고지합니다."
