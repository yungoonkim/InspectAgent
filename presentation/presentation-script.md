### [Slide 3] 시스템 아키텍처: Vision, Decision, Agent의 명확한 역할 분리 (배정 시간: 45초)
*(화면: 3단계 계층 아키텍처 다이어그램 — Vision, Decision, Agent)*

**[발표자 멘트]**  
"VisionInsight는 안전성과 설명력을 동시에 확보하기 위해 시스템을 **3단계 책임 분리 아키텍처**로 구축했습니다.

가장 밑단의 **Layer 1은 Vision 계층**입니다. 900×900 영상 수신 후 OpenCV로 조도를 분석하고, 경량화된 PatchCore 모델로 제품의 이상 점수를 개발 환경 CPU 평균 42.53ms로 계산하여 모델 소견인 `result`를 도출합니다.

가운데 **Layer 2는 Decision 계층**입니다. 비즈니스 로직의 핵심으로, 영상 품질과 모델 결과를 종합하여 6대 우선순위 규칙에 따라 서버 규칙 기반 최종 검사 판정인 `final_result`를 확정하고 JSONL 감사 로그에 영구 기록합니다. 영상 품질 경고 시 제품 결함(NG)과 구분하여 `REINSPECT`로 분류합니다.

상단의 **Layer 3은 Agent 계층**입니다. 검사가 끝난 후, Gemini가 Function Calling으로 조회를 제안하면 서버가 4대 도구를 안전하게 실행하고, 그 결과를 바탕으로 근거 중심의 사후 진단 보고서를 작성하며, 모델의 모든 관측 사실은 서버 메모리에서 1:1 결정적 검증을 거칩니다.

현재 시스템은 서버에서 검사 결과를 생성하고 판정값을 확정하는 프로토타입이며 실제 물리적 PLC, 배출기 제어는 수행하지 않습니다. 또한 AI Agent는 사후 진단 보조 역할만 담당하며 서버의 원본 검사 판정인 final_result를 절대 변경할 수 없습니다."

### [Slide 4] Vision 계층 성능: PatchCore 이상 탐지 실측 결과 (배정 시간: 1분)
*(화면: 핵심 성능 지표 카드 및 83장 테스트 세트 혼동 행렬 분석)*

**[발표자 멘트]**  
"결함 탐지 모델로는 비지도 이상 탐지의 표준인 **PatchCore**를 채택했습니다. 제조 현장에서는 양품에 비해 불량 데이터가 극히 희귀하여 지도 학습을 적용하기 어렵기 때문입니다.

저희는 MVTec Bottle 정상 이미지 180장으로 ResNet-18 기반 메모리 뱅크를 구축했습니다. 체크포인트 크기는 24.18MB이며, 개발 환경(x86_64 CPU)에서 **단일 이미지당 평균 42.53ms**의 추론 지연시간을 실측했습니다. 판정 임계값은 독립 정상 검증 데이터 29장의 이상 점수 분포에 통계적 $\mu + 3\sigma$ 원칙을 적용하여 **34.1442**로 엄격히 고정했습니다.

독립 테스트셋 83장 평가 결과, Image AUROC는 0.8286을 기록했습니다. 주어진 83장 표본에서 TP=32, FP=0으로 정밀도 100%를 보였으나, 이는 실전 공장 환경에서의 전수 보증을 의미하는 것은 아닙니다. 실제 불량 63장 중 31장의 미세 파손과 오염을 놓쳐 재현율(Recall)은 50.79%였습니다. 실제 파손 불량인 T06 시나리오가 점수 32.27로 합격 처리된 것이 대표적인 사례이며, 저희는 이 미탐 한계를 인위적 조작 없이 그대로 보존하고 있습니다."

### [Slide 5] Decision 계층: 대표 판정 규칙 4가지와 REINSPECT 분류 (배정 시간: 1분)
*(화면: `result` vs `final_result` 분리 개념 및 대표 4규칙 카드 + 하단 보충 규칙 박스)*

**[발표자 멘트]**  
"다음은 VisionInsight의 핵심 비즈니스 규칙인 **영상 품질과 결함의 분리**입니다.

저희 시스템에는 두 가지 판정 필드가 있습니다.
`result`는 모델이 제품 외관을 평가한 소견으로 OK, NG, UNKNOWN이 있습니다. 반면 `final_result`는 품질과 시스템 상태를 반영한 최종 판정으로 OK, NG, REINSPECT, ERROR가 있습니다.

저희는 6대 우선순위 계층 중 다음 **대표 4규칙**을 중심으로 작동합니다.
파이프라인 실패 시 Rule 1로 즉시 `ERROR`가 됩니다.
만약 조명이 어두워져서 밝기 경고가 발생했다면, Rule 2에 따라 모델 판정이 OK여도 최종 판정은 **`REINSPECT`, 즉 재검사 필요**가 됩니다. 어두워서 제대로 보이지 않는 상태를 불량으로 단정하지 않고 재검사를 지시하는 오판 방지 핵심 장치입니다.
품질이 정상인 상태에서 PatchCore 이상 점수가 임계값을 초과하면 Rule 4로 `NG [PRODUCT_ANOMALY_DETECTED]`가 되고, 이상 점수가 임계값 이하이면 Rule 5로 `OK [ALL_CHECKS_PASSED]`가 발급됩니다.

슬라이드 하단의 보충 규칙 박스를 보시면, 모델 추론이 미실행된 경우 Rule 3인 `DEFECT_DETECTION_UNAVAILABLE`을 발급해 미탐 제품이 합격 처리되는 것을 차단하며, 정의되지 않은 상태 조합 발생 시 Rule 6인 `UNKNOWN_STATE_COMBINATION`으로 안전 거부합니다.
여기서 REINSPECT는 물리적 폐기나 격리 제어가 아닌 서버 판정 상태 분류입니다."

### [Slide 6] AI Agent: Gemini Function Calling 기반 정밀 조사 체계 (배정 시간: 50초)
*(화면: 도구 호출 흐름 파이프라인 및 4대 Python 도구 카드)*

**[발표자 멘트]**  
"다음은 검사 결과를 운영자에게 알기 쉽게 설명해 주는 Gemini AI Agent입니다.

여기서 핵심은 Gemini가 로컬 코드를 직접 실행하거나 별도의 sandbox 환경을 가동하는 것이 아니라는 점입니다. Gemini는 Function Calling으로 조회 도구와 인자를 제안할 뿐이며, 실제 호출 검증과 Python 도구 실행은 FastAPI AgentService가 담당합니다.

서버가 실행 결과를 Evidence ID와 함께 돌려주면, Gemini는 전달받은 팩트만으로 최종 보고서 초안을 작성합니다.

서버가 제공하는 **4대 전용 조회 도구**는 검사 점수와 판정을 확인하는 `get_inspection_result`, 조도 통계를 보는 `analyze_image_quality`, 단계별 감사 로그를 보는 `get_execution_logs`, 그리고 과거 이력을 보는 `get_inspection_history`입니다.

데이터 격리를 위해 Agent에게는 원본 정답 라벨이나 파일명을 일절 노출하지 않으며, `TARGET-PRODUCT`라는 불투명 별칭만 전달하여 데이터 누수를 차단했습니다."

### [Slide 7] Evidence 메커니즘: 결정적 근거 검증을 통한 신뢰성 확보 (배정 시간: 50초)
*(화면: 4대 신뢰성 축 및 실서버 일치 검증 성과 배너)*

**[발표자 멘트]**  
"생성형 AI를 산업 시스템에 적용할 때 핵심 과제는 환각 억제와 신뢰성 확보입니다.

VisionInsight는 **결정적 근거 검증, Deterministic Grounding**을 구현했습니다.
Gemini가 보고서에서 관측 사실을 작성할 때, 반드시 도구 실행 영수증인 `Evidence ID`(예: `E0001`, `E0002`)와 정확한 데이터 경로인 `JSON Pointer` (`/data/final_result` 등)를 명시해야 합니다.

서버 Python 계층은 JSON Pointer로 참조한 실제 도구 반환값과 모델이 주장한 관측값을 결정적으로 비교합니다. 검증 대상 필드가 일치하지 않으면 서버가 즉시 `EVIDENCE_MISMATCH`, 즉 HTTP 502로 보고서를 거부합니다.

실제 실서버 검증 결과, T01의 관측 사실 6개와 T03의 관측 사실 12개가 서버의 Evidence 검증을 통과했습니다. 저희는 서버에 등록된 필드에 대해 엄밀한 1:1 결정을 보장하는 것이며, 모든 자연어 가설이나 미래의 출력을 완전 무결하게 검증한다고 과장하지 않습니다. 아울러 모델이 최종 판정을 임의로 번복하는 것을 차단했습니다."

### [Slide 8] 기술적 문제 해결: Gemini 구조화 출력 호환성 개선 (배정 시간: 50초)
*(화면: Before 복잡 스키마 vs After 스키마 단순화 + Python 검증 아키텍처)*

**[발표자 멘트]**  
"8번 슬라이드에서는 복잡한 JSON Schema 문제를 해결한 **기술적 아키텍처 구현**을 말씀드리겠습니다.

초기에 최종 진단 보고서를 수신하기 위해 복잡한 Pydantic 구조화 스키마를 Gemini의 `response_json_schema`로 직접 전송했을 때, Gemini 서버로부터 **HTTP 400 ClientError**가 발생했습니다. 정확한 거부 속성은 Google 서버 내부 원인으로 UNKNOWN입니다.

이에 저희는 구조적 Before/After 개선을 단행했습니다.
복잡한 스키마 전체를 Gemini에 강요하는 대신, **극도로 단순화된 JSON 스키마**를 전송하고 서버가 수집한 사실들을 토큰 카탈로그(`K0001~K0006`)로 주입하여 모델은 토큰만 선택하도록 단순화했습니다.

그리고 수신된 출력을 **서버 Python에서 `DiagnosisDraft`로 변환한 뒤, Pydantic과 결정적 Evidence 검증**을 수행하는 파이프라인으로 전환했습니다. 모델 맹신이 아니라 서버 엄격 검증으로 신뢰성을 확보한 기술적 구현이었습니다."

### [Slide 9] 핵심 기술 난제와 해결 과정 (배정 시간: 50초 멘트 / 1분 운영)
*(화면: 3대 핵심 난제 고대비 카드 — HTTP 400, HTTP 504, T05 ERROR + 하단 핵심 교훈 배너)*

**[발표자 멘트]**  
"이어서 개발 과정에서 가장 많은 분석과 재검증이 집중되었던 **3대 핵심 기술 난제와 배운 점**을 회고해 드리겠습니다. Gemini API를 단순히 연결하는 것보다, 검증 가능하고 안전한 Agent를 만드는 것이 훨씬 까다로운 엔지니어링 과제였습니다.

첫 번째 난제는 **구조화 출력의 HTTP 400 오류**였습니다. 복잡한 Pydantic 스키마 거부 현상 앞에서, 'LLM은 생성을 담당하고, 복잡한 타입과 결정적 규칙 검증은 Python 서버가 전담한다'는 아키텍처 원칙을 수립하여 실제 T01/T03 실서버 E2E 완전 성공을 이끌어냈습니다.

두 번째 난제는 **최종 JSON 응답의 HTTP 504 지연**이었습니다. 과거 T03 시나리오에서 도구 조사는 완료되었으나 최종 생성 요청이 15초 제한을 초과해 504 오류가 발생했습니다. 정확한 내부 원인은 UNKNOWN이었으나, 단계별 부하 차이를 계측하여 요청별 timeout을 분리했습니다. 전체 60초 예산을 보존한 채 실험 회차에서 최종 요청에만 30초 timeout을 적용하여 18.967초에 HTTP 200을 수신하고, 전체 24.600초에 E2E PASS를 달성했습니다.

세 번째 난제는 **T05 ERROR 시나리오의 조기 종료 및 근거 검증**이었습니다. 실제 실서버 E2E 검증(`INSP-001405`, `t05_operational_final30_1`) 1회차에서 두 필수 도구 실행으로 실제 오류 이벤트(`IMAGE_LOAD_FAILED`, `INSPECTION_FAILED`)와 17개 원천 근거를 모두 확보했음에도 불필요한 3번째 후속 조사를 시도하다 HTTP 504가 발생하여 **기존 실서버 1회 FAIL**을 기록했습니다. (서버 내부 HTTP 504 원인은 UNKNOWN입니다.) 이에 이미지 로딩 실패 전용 조사 조기 종료 정책을 구현하고 계측기 WARNING 오분류를 정정하여, 오프라인 Mock에서 조사 2회 후 즉시 최종 JSON 보고서로 전환되는 것을 검증하고 **전체 pytest 984개 회귀 테스트를 전원 통과**시켰습니다. 개선 이후 실제 Gemini API 재검증은 아직 수행하지 않은 **실서버 재검증 대기** 상태입니다.

결국 **'AI가 답변을 생성하는 능력보다, 그 답변을 검증하고 근거가 부족할 때 안전하게 거부하거나 불필요한 호출을 조기 종료하는 제어 구조가 중요했다'**는 것이 개발 과정의 핵심 교훈이었습니다."

*(화면: T01 실서버 성공 실측치 vs T03 실서버 성공 실측치 비교표 — 둘 다 PASS)*

정상 병 시나리오인 **T01의 경우, 실제 실서버 E2E 검증에 성공(PASS)**했습니다. 도구 호출과 최종 생성 2회 모두 HTTP 200을 받았고, 전체 시간 약 13.578초 만에 6대 관측 사실이 증명된 진단 보고서를 생성했습니다.

이어 조도 저하 시나리오인 **T03 역시 실서버 E2E 검증에 완전 성공(PASS)**했습니다. 결과 조회 도구(`E0001`)와 품질 분석 도구(`E0002`)를 순차 호출한 뒤, 최종 보고서 생성까지 3회의 HTTP 요청 모두 200 OK를 수신했습니다. 모델이 작성한 12개의 관측 사실은 서버 메모리의 실제 지표와 100% 일치 검증을 통과했습니다. 전체 분석 소요 시간은 24.600초였으며, 9,873토큰을 소비했습니다.

T03의 요청별 실측치를 보면 도구 1에 2.43초, 도구 2에 3.05초가 소요되었고, 최종 단순 JSON 생성 요청은 30초 timeout을 선택 적용하여 18.967초에 수신되었습니다. 과거 15초 요청에서 발생했던 504 오류의 Google 서버 내부 원인은 UNKNOWN이며, 이번 30초 설정 단일 성공으로 향후 안정성을 완전히 보증하는 것은 아닙니다."

### [Slide 11] 발표 데모 시연: T01 양품 vs T03 조도 경고 정적 데모 (배정 시간: 1분 40초 시연 집중)
*(화면: 발표 데모 시연 흐름 제안 및 실제 실서버 진단 보고서 비교)*

**[발표자 멘트]**  
"다음은 시스템 동작 시연입니다. 발표 현장의 네트워크 장애 및 유료 API 호출을 방지하기 위해, 사전에 실서버 검증을 마친 실제 데이터를 재생하는 **독립 실행형 정적 데모(`presentation/demo/`)**를 중심으로 시연합니다.

발표 흐름은 크게 두 단계의 데모 비교로 진행됩니다.
먼저 정상 검사인 **T01 데모 화면**에서는 평균 밝기 135.86에 PatchCore 이상 점수 31.33으로, 모델 판정 OK와 서버 최종 판정 OK(`Rule 5`)가 일치하는 모습을 보여줍니다. 권장 조치인 `CONTINUE_MONITORING`은 실제 판정 팩트인 `F0003`에 정확히 앵커링되어 있습니다.

이어 조도 저하 검사인 **T03 데모 화면**을 시연합니다. 여기서는 평균 밝기가 81.24로 떨어져 `WARNING_LOW_BRIGHTNESS` 경고가 감지됩니다. 모델의 이상 점수는 31.78로 여전히 임계값 미만(모델 OK)이지만, 서버의 규칙 엔진이 즉시 `Rule 2`를 발동하여 최종 판정을 **`REINSPECT(재검사 필요)`**로 분류합니다.

여기서 핵심은 두 검사 모두 모델 판정은 OK지만 서버의 최종 판정이 다르다는 점, 그리고 뒤이어 실행된 Gemini Agent가 도구 2개로 12개 팩트를 확인하되 **서버의 최종 판정(REINSPECT)을 절대 바꾸지 않고 작업자에게 안전한 재검사를 권고한다는 점**입니다."
