### [Slide 3] 시스템 아키텍처: 계층 분리와 단방향 책임 설계 (배정 시간: 45초)
*(화면: 4단계 계층 아키텍처 다이어그램 — Vision, Decision, Storage, Agent)*

**[발표자 멘트]**  
"VisionInsight는 안전성과 설명력을 동시에 확보하기 위해 시스템을 **명확한 책임 분리 아키텍처**로 구축했습니다.

가장 밑단의 **Layer 1은 Vision Core 계층**입니다. 900×900 영상 수신 후 OpenCV로 조도를 분석하고, 경량화된 PatchCore 모델로 제품의 이상 점수를 계산합니다. 개발 환경 x86_64 CPU 단일 이미지 기준 평균 42.53ms가 측정되었으며, 이는 순수 모델 추론 시간입니다.

가운데 **Layer 2는 Decision 계층**입니다. 비즈니스 로직의 핵심으로, 영상 품질과 모델 결과를 종합하여 6대 우선순위 규칙에 따라 서버 규칙 기반 최종 검사 판정인 `final_result`를 확정합니다. 영상 품질 경고 시 제품 결함(NG)과 구분하여 `REINSPECT`로 분류합니다.

**Layer 3은 Storage & Audit 계층**으로, 검사 결과(`data/inspections.jsonl`)와 감사 로그(`data/inspection_logs.jsonl`)를 로컬에 기록하고, 도구 실행 시 Evidence ID를 발급하며, 원본 정답을 완전 격리합니다. 단, 로컬 저장은 개발용이며, 향후 Cloud Run 컨테이너 배포 시 영구 저장은 Cloud Storage(GCS) 연동 과제로 분리되어 있습니다.

상단의 **Layer 4는 Agent 계층**입니다. Gemini가 Function Calling으로 조회를 제안하면 서버가 4대 도구를 안전하게 실행하고, 그 결과를 바탕으로 근거 중심의 사후 진단 보고서를 작성하며, 모델의 모든 관측 사실은 서버 메모리에서 1:1 결정적 검증을 거칩니다.

현재 시스템은 서버에서 검사 결과를 생성하고 판정값을 확정하는 프로토타입이며 실제 물리적 PLC, 배출기 제어는 수행하지 않습니다. 또한 AI Agent는 사후 진단 보조 역할만 담당하며 서버의 원본 검사 판정인 final_result를 절대 변경할 수 없습니다."

### [Slide 4] Vision 엔진 성능: PatchCore 평가 및 엔지니어링 한계 분석 (배정 시간: 1분)
*(화면: 핵심 성능 지표 카드 및 83장 테스트 세트 혼동 행렬 분석)*

**[발표자 멘트]**  
"결함 탐지 모델로는 비지도 이상 탐지의 표준인 **PatchCore**를 채택했습니다. 제조 현장에서는 양품에 비해 불량 데이터가 극히 희귀하여 지도 학습을 적용하기 어렵기 때문입니다.

저희는 MVTec Bottle 정상 이미지 180장으로 ResNet-18 기반 메모리 뱅크를 구축했습니다. 체크포인트 크기는 24.18MB이며, 개발 환경(x86_64 CPU)에서 **단일 이미지당 평균 42.53ms**의 모델 추론 시간을 실측했습니다. 이는 순수 머신러닝 추론 시간이며 Agent 전체 응답 시간이나 생산라인 전체 속도가 아닙니다. 판정 임계값은 독립 정상 검증 데이터 29장의 이상 점수 분포에 통계적 $\mu + 3\sigma$ 원칙을 적용하여 **34.1442**로 엄격히 고정했습니다.

독립 테스트셋 83장 평가 결과, Image AUROC는 0.8286을 기록했습니다. 주어진 83장 표본에서 TP=32, FP=0으로 정밀도 100%를 보였으나, 이는 실전 공장 환경에서의 전수 보증을 의미하는 것은 아닙니다. 실제 불량 63장 중 31장의 미세 파손과 오염을 놓쳐 재현율(Recall)은 50.79%였습니다. 실제 파손 불량인 T06 시나리오가 점수 32.27로 합격 처리된 것이 대표적인 사례이며, 저희는 이 미탐 한계를 인위적 조작 없이 그대로 보존하고 있습니다. 아울러 과거 209장 벤치마크 차이 및 평가 문서의 표기 불일치도 현재 시스템의 제약사항으로 투명하게 남겨두었습니다."

### [Slide 5] Decision 계층: 대표 판정 규칙 4가지와 REINSPECT 분류 (배정 시간: 1분)
*(화면: `result` vs `final_result` 분리 개념 및 대표 4규칙 카드 + 하단 보충 규칙 박스)*

**[발표자 멘트]**  
"다음은 VisionInsight의 핵심 비즈니스 규칙인 **영상 품질과 결함의 분리**입니다.

저희 시스템에는 두 가지 판정 필드가 있습니다.
`result`는 모델이 제품 외관을 평가한 소견으로 OK, NG, UNKNOWN이 있습니다. 반면 `final_result`는 품질과 시스템 상태를 반영한 최종 종합 판정으로 OK, NG, REINSPECT, ERROR가 있습니다.

저희는 6대 우선순위 계층 중 다음 **대표 4규칙**을 중심으로 작동합니다.
파이프라인 실패 시 Rule 1로 즉시 `ERROR`가 됩니다.
만약 조명이 어두워져서 밝기 경고가 발생했다면, Rule 2에 따라 모델 판정이 OK여도 최종 판정은 **`REINSPECT`, 즉 재검사 필요**가 됩니다. 어두워서 제대로 보이지 않는 상태를 불량으로 단정하지 않고 재검사를 지시하는 오판 방지 핵심 장치입니다.
품질이 정상인 상태에서 PatchCore 이상 점수가 임계값을 초과하면 Rule 4로 `NG [PRODUCT_ANOMALY_DETECTED]`가 되고, 이상 점수가 임계값 이하이면 Rule 5로 `OK [ALL_CHECKS_PASSED]`가 발급됩니다.

슬라이드 하단의 보충 규칙 박스를 보시면, 모델 추론이 미실행된 경우 Rule 3인 `DEFECT_DETECTION_UNAVAILABLE`을 발급해 미탐 제품이 합격 처리되는 것을 차단하며, 정의되지 않은 상태 조합 발생 시 Rule 6인 `UNKNOWN_STATE_COMBINATION`으로 안전 거부합니다.
여기서 REINSPECT는 물리적 폐기나 격리 제어가 아닌 서버 판정 상태 분류입니다."

### [Slide 6] AI Agent: Gemini Function Calling 기반 정밀 조사 체계 (배정 시간: 50초)
*(화면: 도구 호출 흐름 파이프라인 및 4대 Python 도구 카드)*

**[발표자 멘트]**  
"다음은 검사 결과를 운영자에게 알기 쉽게 설명해 주는 Gemini AI Agent입니다.

여기서 핵심은 Gemini가 로컬 코드를 직접 실행하거나 별도의 sandbox 환경을 가동하는 것이 아니라는 점입니다. Gemini는 Function Calling으로 조회 도구와 인자를 제안할 뿐이며, 실제 호출 검증과 Python 도구 실행은 FastAPI AgentService가 담당합니다.

서버가 실행 결과를 Evidence ID와 함께 돌려주면, Gemini는 전달받은 팩트만으로 최종 보고서 초안을 작성합니다.

서버가 제공하는 **4대 전용 조회 도구**는 검사 점수와 판정을 확인하는 `get_inspection_result`, 조도 통계를 보는 `analyze_image_quality`, 단계별 감사 로그를 보는 `get_execution_logs`, 그리고 과거 이력을 보는 `get_inspection_history`입니다.

데이터 격리를 위해 Agent에게는 원본 정답 라벨이나 파일명을 일절 노출하지 않으며, `TARGET-PRODUCT`라는 불투명 별칭만 전달하여 데이터 누수를 차단했습니다."

### [Slide 7] Evidence 메커니즘: 결정적 근거 검증을 통한 신뢰성 확보 (배정 시간: 50초)
*(화면: 4대 신뢰성 축 및 실서버 일치 검증 성과 배너)*

**[발표자 멘트]**  
"생성형 AI를 산업 시스템에 적용할 때 핵심 과제는 환각 억제와 신뢰성 확보입니다.

VisionInsight는 **결정적 근거 검증, Deterministic Grounding**을 구현했습니다.
Gemini가 보고서에서 관측 사실을 작성할 때, 반드시 도구 실행 영수증인 `Evidence ID`(예: `E0001`, `E0002`)와 정확한 데이터 경로인 `JSON Pointer` (`/data/final_result` 등)를 명시해야 합니다.

서버 Python 계층은 JSON Pointer로 참조한 실제 도구 반환값과 모델이 주장한 관측값을 결정적으로 비교합니다. 검증 대상 필드가 일치하지 않으면 서버가 즉시 `EVIDENCE_MISMATCH`, 즉 HTTP 502로 보고서를 거부합니다.

실제 실서버 검증 결과, **T01(6개), T03(12개), T05(17개), T06(6개)의 관측 사실 전원이 서버의 Evidence 및 JSON Pointer 검증을 100% 통과**했습니다. 저희는 서버에 등록된 필드에 대해 엄밀한 1:1 결정을 보장하는 것이며, 모든 자연어 가설이나 미래의 출력을 완전 무결하게 검증한다고 과장하지 않습니다. 아울러 모델이 최종 판정을 임의로 번복하는 것을 원천 차단했습니다."

### [Slide 8] 기술적 문제 해결: Gemini 구조화 출력 호환성 개선 (배정 시간: 50초)
*(화면: Before 복잡 스키마 vs After 스키마 단순화 + Python 검증 아키텍처)*

**[발표자 멘트]**  
"8번 슬라이드에서는 복잡한 JSON Schema 문제를 해결한 **기술적 아키텍처 구현**을 말씀드리겠습니다.
