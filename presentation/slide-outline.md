### [Slide 2] 문제 정의: 산업 현장의 과제와 AI 진단의 필요성
- **슬라이드 제목:** 산업 현장의 과제: 규칙 기반 검사의 한계와 AI 진단의 필요성
- **핵심 메시지:** "이상 점수는 산출되지만, 왜 불량인지, 조명 문제인지 운영자는 알 수 없습니다."
- **화면 구성 (2단 비교 카드):**
  - **기존 비전 검사의 주요 한계:**
    - [단순 흑백 판정의 부작용] OK/NG 이분법 판정으로 환경적 조도 변화 시 과도한 오경보(False Alarm) 발생
    - [불투명한 원인 분석] 단순히 불량만 통보되어 조명 문제인지 실제 파손인지 작업자가 즉시 파악 어려움
    - [단순 LLM 도입의 위험성] 외부 생성형 AI를 검사 제어에 직결 시 환각 및 판정 변복 위험 상존
  - **VisionInsight의 해결 접근법:**
    - [PatchCore 기반 이상 탐지] 정상 180장 메모리 뱅크 + 독립 29장 통계 임계값(34.1442)으로 CPU 42.53ms 고속 추론
    - [재검사(REINSPECT) 규칙 분리] 조도 저하 등 영상 품질 경고 시 제품 불량과 구분하여 '재검사 필요'로 분류
    - [Gemini Function Calling 진단] 서버 도구를 직접 호출하여 사실을 수집하고 1:1 결정적 근거로 검증된 보고서 작성
    - [판정 불변 가드레일] Gemini는 사후 진단 보조만 수행하며, 서버가 확정한 판정(final_result)을 절대 변경 불가
- **시간:** 1구간 (Slide 1~3 합계 2분 중 약 45초)

### [Slide 3] 시스템 아키텍처: 계층 분리와 단방향 책임 설계
- **슬라이드 제목:** 시스템 아키텍처: 계층 분리와 단방향 책임 설계
- **핵심 메시지:** "비전 모델, 결정론적 규칙 판정, 생성형 AI Agent의 책임을 엄격히 분리하여 안전성과 설명력을 동시 달성합니다."
- **화면 구성 (4개 수평 계층 다이어그램):**
  - **Layer 1: Vision Core Layer**  
    OpenCV 영상 전처리 & 품질 분석 (밝기 81.24/135.86 등) ➔ PatchCore 이상 탐지 엔진 (ResNet-18) ➔ CPU 단일 이미지 평균 추론 42.53ms
  - **Layer 2: Decision Layer (FastAPI)**  
    고유 검사 식별자 발급 (`INSP-XXXXXX`) ➔ 6대 규칙 기반 종합 판정 (OK / NG / REINSPECT / ERROR) ➔ 영상 품질 경고 시 `REINSPECT` 분리 확정
  - **Layer 3: Storage & Audit Layer**  
    검사 결과(`data/inspections.jsonl`) 및 이벤트 감사 로그(`data/inspection_logs.jsonl`) 로컬 기록 ➔ 도구 실행 시 Evidence ID(`E0001`, `E0002`) 발급 ➔ 정답 완전 격리 *(※ 로컬 저장은 개발용이며, Cloud Run 등 컨테이너 환경의 영구 저장은 Cloud Storage(GCS) 연동 과제로 분리)*
  - **Layer 4: Diagnostic Agent Layer (Gemini)**  
    Function Calling 기반 사후 진단 조회 제안 ➔ 서버의 허용 도구 검증·실행 ➔ 토큰 카탈로그 기반 단순 JSON 생성 ➔ Python 결정적 Evidence 검증 통과 보고서만 운영자 제공
  - *(하단 강조 배너: 현재 시스템은 서버에서 검사 결과를 생성하고 판정값을 확정하는 프로토타입이며 실제 물리적 PLC, 배출기 제어는 수행하지 않습니다. AI Agent는 판정을 변경할 수 없습니다.)*
- **시간:** 1구간 (Slide 1~3 합계 2분 중 약 45초)

### [Slide 4] Vision 엔진 성능: PatchCore 평가 및 엔지니어링 한계 분석
- **슬라이드 제목:** Vision 엔진 성능: PatchCore 평가 및 엔지니어링 한계 분석
- **핵심 메시지:** "불량 데이터 없이 정상 180장만으로 고속 추론을 구현했으나, 미세 결함에 대한 미탐 한계가 존재합니다."
- **화면 구성 (좌측: 핵심 성능 지표 / 우측: 혼동 행렬 및 분석):**
  - **좌측 (핵심 성능 지표, 83장 테스트셋):**
    - [학습 데이터셋] 정상 이미지 180장 (비지도 Coreset 서브샘플링)
    - [임계값 산출셋] 독립 정상 이미지 29장 ($\mu + 3\sigma = 34.1442$)
    - [Image AUROC] **0.8286**
    - [정밀도 Precision] **100.0%** (83장 표본 한정 실측치, 실전 전수 보장 아님)
    - [재현율 Recall] **50.79%** (실제 불량 63건 중 32건 탐지, 31건 미탐)
    - [CPU 단일 추론 시간] **평균 42.53ms** (개발 환경 CPU 단일 이미지 PatchCore 모델 추론 시간이며, 영상 Grab·ROI·FastAPI·Gemini 응답 및 생산라인 배출 제어는 미포함)
  - **우측 (혼동 행렬 및 엔지니어링 분석):**
    - 진양성 (TP): 32건 / 진음성 (TN): 20건 (과검 0건)
    - 위음성 (FN): 31건 (미세 결함 31건 미탐지, 모델 OK != 무결점 제품)
    - T06 미탐 사례 보존: 파손 불량 T06이 점수 32.27로 합격 처리된 한계 정직 보존
    - 평가 문서 제약 보존: 과거 209장(46.17ms) 대비 현재 180장(42.53ms) 차이 및 contamination FN 표기 불일치는 현황 제약으로 보존
    - 정답 격리 & 설비 미제어: 실제 정답 라벨은 Agent에 미제공, 물리적 PLC 제어 미수행
- **시간:** 2구간 (Slide 4~5 합계 2분 중 약 1분)

### [Slide 5] Decision 계층: 대표 판정 규칙 4가지와 REINSPECT 분류
- **슬라이드 제목:** Decision 계층: 대표 판정 규칙 4가지와 REINSPECT 분류
- **핵심 메시지:** "조명이 어두워졌다고 불량품이 아닙니다. VisionInsight는 오판을 방지하고 재검사(REINSPECT)를 지시합니다."
- **화면 구성 (4대 대표 규칙 카드 + 하단 보충 규칙 박스):**
  - Rule 1: 파이프라인 실패 ➔ `ERROR` [`INSPECTION_FAILED`] (영상 로드 실패, 디코딩 에러 등)
  - Rule 2: 영상 품질 경고 ➔ `REINSPECT` [`IMAGE_QUALITY_WARNING`] (조도 저하(T03) 시 모델이 OK여도 재검사 분류)
  - Rule 4: 제품 이상 탐지 ➔ `NG` [`PRODUCT_ANOMALY_DETECTED`] (품질 정상 and 점수 > 34.1442)
  - Rule 5: 정상 검사 통과 ➔ `OK` [`ALL_CHECKS_PASSED`] (품질 정상 and 점수 <= 34.1442)
  - *(하단 보충 규칙 박스: Rule 3 [DEFECT_DETECTION_UNAVAILABLE], Rule 6 [UNKNOWN_STATE_COMBINATION]. REINSPECT는 물리적 폐기/격리 제어가 아닌 서버 판정 상태 분류)*
- **시간:** 2구간 (Slide 4~5 합계 2분 중 약 1분)

### [Slide 6] AI Agent: Gemini Function Calling 기반 정밀 조사 체계
- **슬라이드 제목:** AI Agent: Gemini Function Calling 기반 정밀 조사 체계

### [Slide 8] 기술적 문제 해결: Gemini 구조화 출력 호환성 개선
- **슬라이드 제목:** 기술적 문제 해결: Gemini 구조화 출력 호환성 개선
- **핵심 메시지:** "복잡한 구조화 출력 스키마의 서버 호환성 문제를 확인했고, Gemini 출력 스키마를 단순화한 뒤 Python에서 엄격하게 검증하는 구조로 개선했습니다."
- **화면 구성 (Before vs After 대비 카드):**
  - **Before: 직접 구조화 출력 시도 ➔ HTTP 400**
    - 복잡한 Pydantic 스키마(`DiagnosisDraft`)를 response_json_schema로 직접 전송
    - ➔ Gemini 서버가 스키마 호환성 문제로 ClientError 반환 *(정확한 거부 속성은 UNKNOWN)*
  - **After: 스키마 단순화 + Python 검증 ➔ PASS**
    - 출력 스키마 단순화: Gemini에는 단순화된 JSON 스키마만 전송 (토큰 선택 지시)
    - 토큰 카탈로그 주입: 서버가 수집한 사실(K0001~)을 프롬프트로 전달, 모델은 토큰만 선택
    - Python 엄격 검증 파이프라인: Gemini 출력 ➔ Python DiagnosisDraft 변환 ➔ Pydantic ➔ 결정적 Evidence 검증
